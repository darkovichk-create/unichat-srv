## 1. Назначение проекта

Изначальная задача — заменить ненадёжную зависимость доставки сообщений от широковещательного обмена между клиентами централизованным TCP-сервером-посредником (relay/router). Клиенты должны подключаться к серверу, а сервер — маршрутизировать сообщения адресатам.

Дальнейшая цель — корпоративная централизованная система сообщений для рабочих станций Windows 10 и Windows 11, с возможностью:
- централизованной регистрации клиентов и отображения присутствия;
- обнаружения/регистрации клиентских устройств;
- удалённой настройки адреса и параметров центрального сервера;
- будущей веб-панели администрирования;
- будущих интеграций с внешними системами, включая Елогика на базе Lotus Notes/Domino, для уведомлений о новых заданиях и документах.

Пользователь предпочитает единый инсталлятор, а не отдельную ручную установку клиента и агента. Целевой сценарий — один установочный пакет для рабочего места, который устанавливает/обновляет совместимый клиент и необходимую службу-агент, если выбранная реализация подтвердит необходимость агента. Это архитектурное требование на будущее, ещё не реализовано.

## 4. Известная архитектура и wire protocol исходного сервера

Текущий сервер — C#/.NET 10 TCP relay:
- первый пакет регистрирует подключившегося клиента под его ID;
- пакеты `FORWARD` направляются конкретному клиенту или всем;
- для каждого клиента используется отдельная очередь и writer task;
- пакеты пересылаются без изменения;
- сервер не хранит историю и не доставляет сообщения отключённым пользователям;
- сервер не реализует UDP discovery;
- исходный максимальный размер тела пакета — 128 KiB.

### Формат пакета (по анализу старого клиентского кода)

Клиент формирует пакет примерно так:

```text
SendText(
  IntToStr(Length(AData) + Length(prefix)) +
  prefix + #0 + AData
);

prefix :=
  #0 + CurID + #0 + 'FORWARD' + #0 +
  toUser + #0 + 'UniChat' + #0 + tmp;
```

Структура на проводе приблизительно:

```text
[ASCII-длина][NUL][NUL][ID отправителя][NUL][FORWARD][NUL]
[получатель][NUL][UniChat][NUL][AData]
```

- Получатель `*` означает широковещательную отправку.
- В legacy-формате объявленная длина не включает дополнительный NUL между prefix и AData. Совместимый сервер должен учитывать это правило (исторически используется `advertisedPayloadLength + 1`).
- Не менять framing/семантику без тестов совместимости с реальным клиентом.
- Серверный relay устраняет необходимость прямой доставки peer-to-peer, только если клиенты действительно подключены к нему и клиентский протокол использует этот путь.
- Централизация доставки сама по себе не гарантирует исправление исчезающих списков/чатов: если проблема связана с обнаружением пользователей, надо отдельно изучить discovery и алгоритмы клиента.
- Обнаружение IP/порта не доказывает, что на устройстве запущен UniChat.
- UDP broadcast обычно не проходит через маршрутизаторы и границы VLAN.

### Файлы и вложения

Сервер не имеет отдельного протокола передачи файлов, хранения файлов или возобновления передачи. Он может ретранслировать бинарные данные в `AData` как есть, если клиент уже кодирует их в совместимом формате и размер укладывается в лимит. Не описывать это как реализованный file-transfer.

## 7. Принятые архитектурные решения (план, ещё не реализация)

Принята гибридная стратегия: сначала обеспечить совместимость с существующим UniChat, параллельно проектировать расширяемую корпоративную платформу и при необходимости новый клиент с привычным интерфейсом. Не переписывать клиент до завершения исследования его протокола и конфигурации.

### Серверные компоненты

Планируемые логические подсистемы:
- **Client Registry** — реестр устройств и клиентских идентификаторов;
- **Presence Service** — онлайн/оффлайн, heartbeat и последнее время активности;
- **Device Management** — состояние и управление зарегистрированными устройствами;
- **Configuration Service** — выдача и версионирование конфигураций;
- **Message Router** — централизованная маршрутизация сообщений;
- **Audit Log** — журнал административных действий и изменений конфигурации;
- **Management API** — отдельный HTTPS API для будущей веб-панели и интеграций;
- **Integration API/Event ingress** — приём внешних событий через аутентифицированный HTTPS API.

Не смешивать административный HTTPS API с legacy TCP wire protocol. Предусмотреть возможность независимого масштабирования и версионирования.

### Обнаружение и регистрация клиентов

Предпочтительный вариант при разрешённой централизованной установке — Windows-служба-агент, поставляемая единым инсталлятором с клиентом/компонентами рабочего места:
- агент регистрирует устройство на сервере;
- отправляет heartbeat и сведения о версии/состоянии;
- получает утверждённую конфигурацию;
- применяет адрес/порт центрального сервера и другие разрешённые параметры;
- сообщает результат применения и поддерживает безопасный откат.

Дополнительные механизмы:
- UDP discovery в локальной сети как вспомогательный механизм;
- DNS SRV или заранее заданный адрес/конфигурация установщика как способ первичного нахождения сервера;
- GPO/AD могут использоваться для централизованного развёртывания единого установщика, если инфраструктура доменная;
- сканирование подсетей не считать достоверным обнаружением запущенного клиента и использовать только как ограниченный вспомогательный механизм.

### Единый инсталлятор

Требование пользователя: единый инсталлятор рабочего места вместо раздельной установки клиента и агента. При проектировании определить:
- состав пакета и поддерживаемые варианты установки/обновления;
- установку/обновление агента как Windows Service;
- права администратора и минимальные привилегии службы;
- корректное удаление, repair и rollback;
- безопасную первоначальную регистрацию устройства;
- подпись установщика и обновлений;
- совместимость с Windows 10 и Windows 11;
- сценарии централизованного развёртывания через GPO/AD;
- возможность установки только совместимого клиента или только компонентов по политике, если это понадобится.

Не проектировать произвольное удалённое выполнение команд на рабочих станциях. Агент должен принимать только ограниченный набор подписанных/аутентифицированных декларативных настроек и безопасных операций.

### Безопасность управления

Обязательные требования:
- аутентификация устройств и сервера;
- авторизация по ролям;
- TLS для HTTPS API и управляющего канала;
- защищённая регистрация устройства и ротация секретов/сертификатов;
- подпись или криптографическая проверка конфигураций;
- аудит выдачи и применения настроек;
- версии конфигураций, подтверждение применения и rollback;
- запрет произвольных shell-команд;
- принцип минимальных привилегий.

### Будущие интеграции

Не связывать ядро сервера напрямую с Lotus Notes. Предусмотреть универсальный Integration API/event ingress и адаптеры. Для Елогика / Lotus Notes-Domino позже потребуется определить доступный интерфейс интеграции (HTTP/API, агент, почтовое событие или иной поддерживаемый механизм), схему идентификаторов сотрудников и подтверждение доставки уведомлений.

Базовая модель: внешняя система передаёт событие (например, новое задание или документ), сервер сопоставляет внешний ID сотрудника с UniChat ID и создаёт уведомление. Нужны идемпотентность, журнал обработки, авторизация источника и статусы доставки. Реализация интеграции отложена.

## 12. Статическая проверка framing и исходников — 2026-11-25

**Ветка:** `fix/tcp-framing-and-deployment`  
**Проверенный blob ClientConnection.cs:** `d9e7bbdf00325fada07e7b01c62e1f8d1d7c5754`

### Уточнение расчёта длины пакета

Ранее возникло предположение, что `advertisedPayloadLength + 1` в исправленной ветке может быть лишним. Повторная сверка с формулой оригинального клиента это предположение опровергла.

Клиент формирует:

```text
IntToStr(Length(AData) + Length(prefix)) + prefix + #0 + AData
prefix := #0 + CurID + #0 + 'FORWARD' + #0 + toUser + #0 + 'UniChat' + #0 + tmp
```

Поскольку `prefix` уже включает начальный NUL, а после него клиент добавляет ещё один NUL перед `AData`, число байтов после NUL-разделителя заголовка равно объявленной длине плюс один. Следовательно, текущая операция `advertisedPayloadLength + 1` в ветке исправлений соответствует legacy-формату. **Не удалять её без теста на пакетах, сформированных оригинальным клиентом.**

### Подтверждённые наблюдения

- `ReadHeaderAsync` в ветке исправлений читает заголовок до NUL и не предполагает, что TCP вернёт 16 байт одним чтением.
- После заголовка код дочитывает точное число байтов тела.
- `TryParsePrefix` разбирает первые четыре поля: пустое начальное поле, ID отправителя, команду и получателя.
- `ConnectionManager` хранит только активные TCP-соединения в ConcurrentDictionary; офлайн-очереди и история отсутствуют.
- Широковещательная отправка проходит по текущим активным соединениям, включая отправителя, если он зарегистрирован в словаре.
- Первый пакет устанавливает ClientId; в исправленной ветке последующие пакеты с отличающимся ID отклоняются.
- `RefCountedBuffer` использует ArrayPool и счётчик ссылок для совместного использования одного буфера между очередями адресатов.
- Настройки клиента из найденных batch/registry файлов расположены под `HKCU\\Software\\UniChat145`; сетевые настройки экспортируются из подраздела `Network`. Имена конкретных параметров сервера пока не установлены.

- Для каждой сессии создана отдельная ограниченная исходящая очередь ёмкостью 256 пакетов.
- При невозможности поставить пакет в очередь соединение закрывается; это ограничивает бесконтрольный рост очередей при медленном/зависшем получателе.
- Максимальный размер тела одного пакета ограничен 128 KiB.
- Пакет маршрутизируется как неизменённый буфер; broadcast проходит по текущим зарегистрированным соединениям.
- TCP Keep-Alive включён; параметры сокета: 30 секунд до первой пробы и 10 секунд между пробами.
- В текущем коде реестр отражает подключённые TCP-сессии; отдельного Presence Service, heartbeat API или постоянного реестра устройств пока нет.
- Обработчики клиентских сессий запускаются фоновыми задачами; listener не хранит отдельный реестр этих задач для ожидания их завершения при остановке. Это следует проверить тестом штатной остановки/перезапуска при открытых соединениях.

### Приоритеты следующего этапа

1. Автоматизировать протокольные тесты: регистрация, личная доставка, broadcast, некорректный/неполный пакет, дубликат ClientId, переполнение очереди.
2. Проверить повторные подключения, параллельные сессии и штатную остановку сервера с активными клиентами.
3. Провести ограниченный нагрузочный/длительный тест с постепенным увеличением числа синтетических клиентов; отдельно фиксировать CPU, RSS, число соединений, рестарты и ошибки.
4. Только после базовой проверки устойчивости менять lifecycle/очереди, если тесты покажут проблему.
5. Presence и управление устройствами реализовывать отдельным новым компонентом/протоколом, не выдавая текущий TCP-реестр за полноценную систему присутствия.

## 21. SQLite-журнал сессий, маршрутизации и ошибок с хранением 20 дней — 2026-11-25

**Ветка:** `fix/tcp-framing-and-deployment`  
**Компоненты:** `AuditLog.cs`, `ClientConnection.cs`, `ConnectionManager.cs`, `TcpServerListener.cs`, `Program.cs`, `UniChatServerd.csproj`.  
**Хранилище на VM:** `/var/lib/unichatd/audit.db`.  
**Режим хранения:** SQLite WAL, UTC timestamps (Unix milliseconds), retention 20 дней.

### Что реализовано

- Добавлен отдельный hosted service `AuditLog`, который асинхронно принимает события из сетевого кода через ограниченную очередь ёмкостью 8192 записи и записывает их пакетами до 128 событий.
- SQLite работает в WAL-режиме; созданы таблица `audit_events` и индексы по времени, ClientId и SessionId.
- Старые события старше 20 дней удаляются при запуске и далее не реже одного раза в час. Выполняется инкрементальная очистка свободных страниц и WAL checkpoint.
- Сбой или временная недоступность БД не должны останавливать TCP relay: AuditLog повторяет подключение с интервалом 5 секунд; при переполнении очереди фиксирует предупреждения о потерянных событиях.
- При штатном завершении очередь журнала закрывается и оставшиеся записи сбрасываются в SQLite.
- В Linux systemd unit добавлен `StateDirectory=unichatd`; каталог БД закрыт правами владельца службы (`0700`), файлы SQLite — `0600`.
- Для self-contained single-file publish включён `IncludeNativeLibrariesForSelfExtract=true`, а `DOTNET_BUNDLE_EXTRACT_BASE_DIR` направлен в `/var/lib/unichatd/.net`.

### Состав аудита и приватность

Сохраняются:
- UTC-время события с точностью до миллисекунд;
- открытие/регистрация/закрытие TCP-сессии, ClientId, IP-адрес и длительность сессии;
- protocol/framing errors, сетевые ошибки, неизвестные команды, дубликаты ClientId, нарушения привязки ID и переполнение очереди;
- маршрутизация личных и broadcast-пакетов, адресат, размер пакета и результат постановки в исходящую очередь;
- запуск/остановка сервера и предупреждения при завершении.

**Тело сообщений и содержимое вложений не сохраняются.** Для сообщений записываются только метаданные. Результат `queued_to_socket_queue(s)` означает постановку в очередь сервера, а не подтверждение фактического получения клиентом.

### Дополнительное исправление жизненного цикла сессий

- `TcpServerListener` теперь отслеживает задачи всех клиентских сессий.

## 30. Уточнение сигнатуры UDP builder 0x579724 — 2026-11-25

### Исправление формулировки раздела 29

- Повторная проверка вызывающих участков показала, что второй аргумент функции `0x579724` в EDX — **указатель на вторую строку**, а не длина.
- Первый аргумент в EAX — указатель на первую строку. Функция сохраняет второй указатель в EBX, затем вызывает helper `0x405270` для получения/обработки длины первой строки; полученное значение участвует в сравнении с 100.
- Поэтому `0x579724` следует описывать как сборщик/отправитель, принимающий две строки (или две Delphi AnsiString), а не как функцию с сигнатурой `(buffer, length)`.
- Внутри функция формирует служебную последовательность, объединяя первую и вторую строки с константными строками/префиксами. В отдельных ветках записывает ASCII `'0'` или `'1'` в локальный буфер; ветвление зависит от длины первой строки.
- После сборки wrapper `0x560F38` отправляет итоговую строку через Winsock `send` на UDP socket handle `0x5984A0`.
- Call sites передают в EDX разные строковые значения: в ряде мест — поля объекта по смещениям `+0x32C` или `+0x324`; в других — указатели на статические Delphi string constants. Это подтверждает, что второй аргумент является строковым фрагментом/значением, а не числовой длиной.

### Значение для дальнейшего анализа

- При восстановлении wire format нужно отслеживать оба строковых аргумента и все конкатенации, а не трактовать EDX как packet length.
- Вызовы `0x579724` встречаются в нескольких разных участках приложения; до анализа контекста каждого call site нельзя сводить их к одному типу события.
- Исправление относится к сигнатуре helper; наблюдения о вызове UDP send через `0x560F38`, socket handle `0x5984A0` и использовании строковых констант остаются подтверждёнными.

## 32. Установлено назначение флага 0x595CB4: Network/IsServer — 2026-11-25

### Источник флага в конфигурации

- Функция загрузки настроек по VA `0x575500` читает INI-секцию `Network`.

### Значение для общего builder/dispatcher 0x579724

- Ранее найденный branch condition по `0x595CB4` теперь имеет установленный конфигурационный источник: это `Network/IsServer`.

Таким образом, серверный режим использует отдельный socket-object send path, а клиентский режим — явно выделенный UDP socket handle.
- Тип сокета альтернативного object path пока не подтверждён непосредственно через его constructor/setup call graph; поэтому не называть его TCP без дополнительной трассировки, хотя в бинарнике отдельно обнаружен TCP stream path.

## 33. Восстановлены параметры UDP broadcast из Network INI — 2026-11-25

### Точное соответствие глобальных переменных INI-настройкам

- Функция загрузки настроек по VA `0x575500` читает строковое значение `Port` из секции `Network`, default string `17889`, и сохраняет его в глобальную строковую переменную по адресу `0x595B64`.

- Следовательно, `Network/Port` и `Network/BroadcastIP` — именно параметры UDP broadcast endpoint; `DedicatedIP` и `DedicatedPort` относятся к отдельной dedicated-серверной конфигурации. Не смешивать эти пары.

### Передача значений в UDP socket setup

- Вызов `0x560E34` по адресу `0x58D25C` получает:
  - EAX: результат преобразования строки `Network/Port` из `0x595B64` в integer через helper `0x409C04`;
  - EDX: строковое значение `Network/BroadcastIP` из `0x595E58`;
  - ECX: HWND, полученный из объекта главной формы.
- Аналогичный вызов `0x560E34` присутствует в другом lifecycle path по адресу `0x584DCD`, который также передаёт integer port, IP string и window handle.
- Внутри `0x560E34` создаются два UDP-сокета `socket(AF_INET, SOCK_DGRAM, IPPROTO_UDP)`.
- Для исходящего сокета `0x5984A0` формируется sockaddr с family AF_INET, портом через `htons(EAX)` и адресом через `inet_addr(EDX)`, после чего выполняется UDP `connect`.

- Это подтверждает, что default UDP peer — broadcast address `255.255.255.255`, а default local UDP port — `17889`, если соответствующие значения не переопределены в `unichat.ini`.

### Значение для архитектуры протокола

- В клиенте явно разделены две конфигурационные пары:
  - UDP broadcast: `Network/BroadcastIP` + `Network/Port` (defaults `255.255.255.255:17889`);

## 35. Восстановлен TCP stream framing и внутренний UniChat marker — 2026-11-25

### TCP ClientRead и reassembly

- Published callback `ClientRead` связан с обработчиком по VA `0x58CF3C`.
- Обработчик вызывает `0x55C6B4`, который выполняет Winsock `recv` через thunk `0x4B8088` (IAT `wsock32.recv`) на socket handle из поля объекта `+4`.
- Вызов принимает буфер размером `0xFF69` байт (65385).
- Если предыдущий фрагмент был неполным, он хранится в глобальном буфере/счётчиках (`0x595B24`, `0x595F54`, флаг `0x595E34`) и объединяется с новыми принятыми байтами.
- Обработчик не предполагает соответствие одного `recv` одному сообщению. Он вычисляет границу полного сообщения, обрабатывает полные сообщения в цикле и сохраняет незавершённый остаток для следующего callback. Это подтверждает TCP stream reassembly и поддержку нескольких сообщений в одном read buffer.

### Внешнее stream framing

- В начале накопленного TCP stream обработчик ищет первый NUL-терминированный ASCII-префикс: он извлекает строку до NUL и преобразует её в integer через helper `0x409C04`.
- Длина префикса и полученное числовое значение используются для вычисления ожидаемой границы кадра: `prefix_length + parsed_integer + 1`.
- Если доступных байтов больше ожидаемой длины, текущий кадр отделяется, передаётся дальше, остаток сдвигается/сохраняется, затем цикл проверяет следующий кадр.
- Если доступных байтов меньше ожидаемой длины, буфер сохраняется как неполный фрагмент.
- Точное соглашение о том, включает ли parsed integer завершающий NUL payload или иные служебные байты, требует проверки по outgoing builder; в этом разделе фиксируется только фактически используемая формула и поведение reassembly.

### Внутренняя структура кадра

- Полный кадр передаётся в parser по VA `0x58CCD4`.
- Parser сканирует данные на девятибайтовый sentinel `00 55 6E 69 43 68 61 74 00`, то есть `NUL + "UniChat" + NUL`.
- Сразу после sentinel копируются четыре байта в integer length field; далее payload извлекается с позиции `sentinel_offset + 15`. Это соответствует 9 байтам sentinel + 4 байтам length + 2 байтам смещения до начала payload по наблюдаемой адресной арифметике; окончательную byte-exact схему следует сверить с builder.
- В извлечённом payload читается byte offset 4. При значении ASCII `'1'` выполняется отдельная ветка; в остальных случаях из payload извлекается остаток, начиная с шестого символа (Delphi 1-based index 6, то есть byte offset 5), и передаётся общему parser `0x5820C0`.
- Таким образом, TCP receive path подтверждает внутренний пятый байт discriminator, уже найденный в UDP receive path, и общий NUL-delimited parser для остатка данных.

### Связь с UDP

- UDP receive path `0x5826D4` отдельно получает датаграмму и также проверяет byte offset 4 на ASCII `'1'`, после чего направляет альтернативную ветку в `0x5820C0`.
- TCP path содержит дополнительный stream framing и sentinel/length parsing до извлечения внутреннего payload.
- Это указывает на общий внутренний формат сообщений поверх двух транспортов, но не доказывает полную идентичность всех полей или byte-for-byte идентичность TCP и UDP пакетов.

## 36. GroupKey участвует в общем 12-байтовом преобразовании сетевых данных — 2026-11-25

### Источник ключа

- При загрузке конфигурации функция `0x575500` читает `GroupKey` из секции `Security` и сохраняет строку в глобальную переменную `0x595A18`.
- Это значение передаётся в helper `0x5610C8` как входная строка.

### Поведение helper 0x5610C8

- Helper нормализует входную строку к 12 байтам:
  - при длине ровно 12 байт копирует все 12;
  - при длине меньше 12 формирует 12-байтовую область с заполнением `0xFF` и копирует исходные байты;
  - при длине больше 12 использует первые 12 байт.
- Затем три 32-битных слова преобразуются серией операций, включающих XOR с константами, rotate, byte-swap, AND и OR. Набор некоторых операций управляется битами второго аргумента (EDX).
- Результат записывается в выходную Delphi string/буфер длиной 12 байт.
- Это собственный key-dependent transform оригинального клиента. По одному дизассемблированию нельзя приписывать ему стандартный криптографический алгоритм или гарантировать криптографическую стойкость.

### Подтверждённые сетевые call sites

- Исходящий builder `0x579724` вызывает `0x5610C8`, передавая строку из `0x595A18`, 32-битное значение, полученное через helper `0x40362C` с аргументом `0x7FFFFFFF`, и локальный output buffer.
- UDP receive processing вызывает тот же helper по адресу `0x58280D`: передаёт `GroupKey`, 32-битное значение из разобранного входящего пакета и локальный output buffer.

- Таким образом, GroupKey-dependent transform встречается в исходящем builder и в обоих входящих transport paths. Это подтверждает, что GroupKey является частью сетевой обработки, а не только локальной настройкой UI.

### Что пока неизвестно

- Не установлено, является ли результат MAC/check value, маскировкой/обфускацией, ключевым преобразованием заголовка или частью другого протокольного механизма.

- Не восстановлены точные байтовые позиции 12-байтового результата в отправляемой датаграмме/кадре и проверка результата на приёме.

## 39. Уточнены параметры RC6 Init: 96-bit derived key и нулевой IV — 2026-11-25

### Идентификация virtual methods

- Глобальный cipher object `0x598644` хранит экземпляр с VMT, связанным с RTTI `TDCP_rc6`.
- В VMT RC6 slot `+0x40` указывает на функцию `0x49DFFC`. Она принимает key string в EDX, key size в ECX и дополнительный IV pointer на стеке.
- Функция `0x49DFFC` передаёт key/key size в базовый cipher initialization path, выполняет RC6 key schedule через virtual method и инициализирует IV.
- При нулевом IV pointer метод заполняет 16 байт внутреннего IV buffer по offset `+0x38` нулями и вызывает дальнейшую инициализацию cipher state.
- В outgoing builder `0x579724` перед вызовом VMT slot `+0x40` на стеке остаётся явный аргумент `0`; helper `0x4052D8` возвращается обычным `ret`, не удаляя этот аргумент. Поэтому для этого вызова IV pointer равен NULL.
- В receive paths повторяется такой же вызов: GroupKey-derived key и key size `0x60` (96 bits), с нулевым IV pointer.

### Ключ и nonce

- Outgoing builder получает 32-битное значение через `0x40362C(0x7FFFFFFF)`, сохраняет его четыре байта и передаёт это значение вместе с `Security/GroupKey` в `0x5610C8`.
- Helper `0x5610C8` выдаёт 12-байтовую строку, которая передаётся в RC6 Init с key size `0x60` = 96 bits.
- UDP receive path извлекает первые четыре байта входящей датаграммы и передаёт их вместе с тем же GroupKey в `0x5610C8`, после чего также инициализирует cipher object 96-битным ключом.
- Это подтверждает per-message key derivation от GroupKey и четырёхбайтового packet value. Точное имя этого поля (nonce/packet ID) в оригинальном протоколе пока не установлено.

### Cipher mode

- Конструктор RC6 object `0x49DE0C` явно устанавливает byte field `[object+0x34] = 0`.
- Базовый cipher code читает этот field как индекс режима и поддерживает пять enum значений из RTTI: `cmCBC`, `cmCFB8bit`, `cmCFBblock`, `cmOFB`, `cmCTR`.
- Первое enum значение `cmCBC` имеет ordinal 0; следовательно, default mode нового RC6 object — CBC.
- В исследованном сетевом lifecycle не обнаружен вызов setter, который переключал бы mode после конструктора. Поэтому CBC является установленным default для созданного сетевого cipher object, пока не найдена другая запись в этот field.

### Ограничения

- 16-байтовый zero IV подтверждён для вызовов Init без IV pointer.
- Точный padding/alignment ciphertext пока не восстановлен. Wrapper выделяет output string по длине input string; block processing и обработка остатка требуют отдельного анализа.
- Не следует автоматически считать, что весь внешний TCP frame или все 5 байт внутреннего header зашифрованы: parser читает header discriminator до decrypt path.
- Хотя outgoing и incoming calls соответствуют encrypt/decrypt направлениям, окончательную byte-level совместимость нужно подтвердить парными тест-векторами.

### Следующие действия

1. Восстановить exact outgoing plaintext, ciphertext и 5-byte inner header offsets.
2. Разобрать RC6 CBC block processing для длины, не кратной 16, и установить padding policy.
3. Подтвердить, что TCP parser использует тот же 96-bit derived key и нулевой IV для каждой отдельной frame.

5. Только после совпадения тест-векторов реализовывать совместимость в сервере.


## 40. Уточнён реальный RC6 режим сети и восстановлена компрессионная оболочка — 2026-11-25

### Коррекция режима шифрования из раздела 39

- Поле `[object+0x34]` в конструкторе действительно устанавливается в 0, а RTTI enum содержит `cmCBC` первым. Однако это не доказывает, что сетевой builder использует generic CipherMode dispatcher.
- Сетевой outgoing wrapper по VMT slot `+0x54` (функция `0x49DCFC`) вызывает непосредственно slot `+0x7C` RC6 VMT, то есть функцию `0x49E37C`.
- Сетевой incoming wrapper по VMT slot `+0x58` (функция `0x49DD3C`) вызывает непосредственно slot `+0x80`, то есть функцию `0x49E41C`.
- `0x49E37C` обрабатывает данные побайтно: получает 16-байтовый keystream block через RC6 block routine, XOR-ит первый байт с входным байтом, сдвигает 16-байтовое состояние на один байт и добавляет выходной ciphertext byte.
- `0x49E41C` выполняет обратный путь: сохраняет входной ciphertext byte, XOR-ит его с первым keystream byte, сдвигает состояние и добавляет сохранённый ciphertext byte.
- Это соответствует паре RC6-CFB8bit encrypt/decrypt routines. Сетевой код вызывает эти slots напрямую, минуя generic mode switch; поэтому активный network mode — **CFB8bit**, а не CBC. Утверждение о CBC как активном режиме из раздела 39 считать исправленным.
- Key derivation и Init остаются прежними: GroupKey + 4-byte packet value -> 12-byte key, key size 96 bits; IV pointer NULL, внутреннее 16-byte IV state обнуляется.
- Output string length задаётся равной input length; CFB8bit обрабатывает произвольное число байтов, поэтому PKCS#7/block padding в этом path не требуется.

### Значение byte[4]: compression flag

- В outgoing builder `0x579724` при длине исходной строки меньше 100 байт записывается ASCII `'0'`; строка передаётся в RC6-CFB8bit без compression envelope.
- При длине 100 байт и более записывается ASCII `'1'`; перед RC6 encryption вызывается `0x56F434`, который формирует compression envelope.
- В receive path после RC6 decryption значение byte[4] проверяется:
  - `'0'`: plaintext передаётся далее без decompression;
  - `'1'`: вызывается `0x56F4D4`, который разбирает compression envelope и при необходимости распаковывает данные.
- Следовательно, byte[4] — compression-path discriminator, а не произвольный тип сообщения.

### Формат compression envelope

- `0x56F434` получает plaintext, длину и параметр `10`; внутри вызывает compressor helper `0x56ED7C`, который проверяет допустимый диапазон параметра 1..10 и формирует compressed output.
- Если compressed data короче исходной, в начало envelope записывается 4-byte little-endian исходная длина, далее идут compressed bytes; output length равен compressed_length + 4.
- Если compression не уменьшает размер, в первые четыре байта записывается ноль, затем копируется исходный plaintext; output length равен original_length + 4.
- Receive helper `0x56F4D4` читает первые четыре байта:
  - ненулевое значение задаёт ожидаемый размер распакованного plaintext, а оставшаяся часть передаётся decompressor `0x56F194`;
  - ноль означает, что оставшаяся часть уже является исходными данными и копируется без распаковки.
- Декомпрессор `0x56F194` содержит bitstream/Huffman parsing, literal decoding и LZ back-reference copy path, что соответствует DEFLATE-family stream. Точный wrapper/checksum и byte-for-byte соответствие конкретной zlib версии пока не установлены.

### Итоговый inner payload path (на текущем уровне доказательств)

1. Outgoing: generate 4-byte packet value.
2. Derive 12-byte key from `Security/GroupKey` + packet value.
3. Initialize TDCP_rc6 with 96-bit key and zero IV.
4. For long messages (>=100 bytes), optionally compress into 4-byte-size-prefixed envelope; mark byte[4] as `'1'`. Short messages use `'0'` and skip compression envelope.
5. Encrypt body using RC6-CFB8bit; prepend 4-byte packet value + 1-byte compression flag.
6. Incoming: read 4-byte packet value and byte[4], derive same key, initialize cipher, decrypt body; if flag is `'1'`, decode compression envelope; pass plaintext fields to common NUL-delimited parser.

### Следующие действия

1. Проверить точные byte offsets внешнего TCP marker/length относительно этого inner payload.
2. Проверить, что compression parameter 10 и DEFLATE envelope одинаковы на TCP и UDP send paths.
3. Создать offline test vectors для short plaintext, compressible long plaintext и incompressible long plaintext.
4. Проверить round-trip RC6-CFB8bit с GroupKey, packet value и zero IV, не запуская оригинальный EXE.
5. После совпадения векторов подготовить протокольную спецификацию и synthetic tests для server relay; production код пока не менять.


## 41. Детализирован custom GroupKey/packet-ID key derivation — 2026-11-25

### Нормализация GroupKey

- Helper `0x5610C8` получает GroupKey string, 32-bit seed и output string variable.
- Входная Delphi AnsiString нормализуется к 12 байтам:
  - ровно 12 байт — копируются без изменений;
  - меньше 12 байт — справа дополняется байтами `0xFF`;
  - больше 12 байт — используются первые 12 байт;
  - пустая строка после fill path даёт 12 байт `0xFF`.
- Нормализованные 12 байт читаются как три little-endian DWORD: A = bytes[0..3], B = bytes[4..7], C = bytes[8..11].

### Seed и преобразование

- Outgoing builder получает seed через `0x40362C(0x7FFFFFFF)`, сохраняет его 4 байта и использует тот же DWORD при вызове `0x5610C8).
- Receive path извлекает соответствующие первые четыре байта пакета и передаёт их как seed в тот же helper.
- Seed используется как 32-битная битовая маска: по отдельным битам 0..31 условно выполняются операции над A/B/C.
- Преобразование включает фиксированные XOR-константы, conditional XOR, ROL/ROR, BSWAP, AND, OR и NOT; часть операций выполняется безусловно, часть зависит от конкретного seed bit.
- В конце helper записывает преобразованные DWORD в shortstring/output buffer в порядке **B, A, C**, затем преобразует результат в Delphi AnsiString.
- Результат — 12 байт, которые сетевой код передаёт в RC6 Init с key size 96 bits.

### Значение для совместимости

- Это не стандартный KDF (HKDF/PBKDF2 и т.п.), а собственный детерминированный 32-bit seed-dependent transform оригинального UniChat.
- При одинаковых raw GroupKey bytes и packet ID результат детерминирован; отправитель и получатель могут независимо получить один и тот же RC6 key.
- Packet ID выполняет две роли: участвует в derivation 96-bit RC6 key и используется packet-filter/replay logic.
- Seed генерируется через helper с верхней границей `0x7FFFFFFF`; криптографическую непредсказуемость генератора пока не оценивали. Не считать этот nonce криптографически стойким без анализа PRNG.
- Кодировка GroupKey определяется Delphi AnsiString bytes; Unicode normalization или UTF-8 conversion в этом helper не обнаружены.

### Реализация и проверка

- Полная последовательность операций находится в VA `0x5610C8–0x5613FB`.
- Точная транслитерация возможна, но независимого output vector от оригинального EXE пока нет, так как неизвестный бинарник не запускался. Не объявлять самодельный port подтверждённым до сравнения с безопасно полученным эталонным результатом.

## 42. Уточнён формат compressed payload: raw DEFLATE stream — 2026-11-25

### Декомпрессор 0x56F194

- После 4-byte uncompressed-size envelope header функция `0x56F4D4` передаёт оставшиеся bytes в `0x56F194`.
- `0x56F194` читает DEFLATE bitstream непосредственно с первого переданного байта: анализирует BFINAL/BTYPE, обрабатывает stored/fixed/dynamic Huffman blocks, literal symbols, length codes и distance/back-reference copy.
- В этом вызове не обнаружено предварительного пропуска zlib/gzip header или последующей проверки Adler32/CRC trailer.
- Следовательно, compressed payload соответствует raw DEFLATE/RFC1951-style stream, а не полноценному gzip container. Zlib wrapper не подтверждён.
- Compressor helper `0x56ED7C` формирует данные, которые затем напрямую передаются этому decoder; по согласованной структуре envelope это raw DEFLATE output.

### Подтверждённый compression envelope

- 4-byte little-endian prefix:
  - ненулевое значение — ожидаемая длина распакованного plaintext, далее raw DEFLATE stream;
  - ноль — следующие bytes являются исходным plaintext без компрессии.
- Внешний inner-header byte[4] со значением ASCII `'1'` означает, что после decrypt нужно обработать этот 4-byte envelope; `'0'` означает, что envelope отсутствует.
- Компрессионная ветка включается при исходной длине от 100 байт; compressor использует параметр `10`. Если compressed data не короче исходного, записывается zero-size marker и исходные данные копируются без компрессии.

### Ограничения

- Точный вариант RFC1951 encoder (strategy, window size, block selection и соответствие известной реализации) пока не установлен.
- Проверка checksum не обнаружена; целостность/аутентификация данных, вероятно, обеспечивается отдельными packet/cipher mechanisms, но это требует отдельной проверки.


## 43. Разобран outgoing TCP wrapper и выявлена асимметрия с ClientRead parser — 2026-11-25

### Внешнее TCP stream prefix

- TCP receive callback `ClientRead` / `0x58CF3C` ищет первый NUL, извлекает предшествующую ASCII decimal string и преобразует её в integer.
- Для полного stream frame используется вычисление `prefix_length + parsed_integer + 1`; неполные frames сохраняются для следующего read, а несколько полных frames обрабатываются циклом.
- В TCP send path функции `0x579724` вычисляется сумма длин двух подготовленных строковых блоков, значение преобразуется в decimal через `0x409AC8` и используется как length prefix при финальной конкатенации перед вызовом TCP send wrapper `0x55C340`.
- Это подтверждает decimal length-prefixed TCP stream protocol. Точный учёт одного дополнительного NUL между сегментами требует дальнейшей проверки по runtime/test vector; пока не фиксировать окончательную формулу payload length.

### Наблюдаемые части outgoing TCP payload

- В TCP branch builder создаёт inner encrypted packet: 4-byte packet value + compression flag byte ('0'/'1') + RC6-CFB8bit ciphertext.
- Отдельно формируется metadata string с участием:
  - global string `0x5959B0`;
  - NUL separator;
  - literal `\0FORWARD\0`;
  - второй строковый аргумент builder;
  - literal `\0UniChat\0`;
  - копия 4-byte packet value с завершающим NUL.
- Финальная TCP string содержит decimal length prefix, metadata и inner packet; отправляется через TCP wrapper `0x55C340`.
- В UDP branch такого TCP wrapper нет: отправляется inner packet напрямую через UDP `send`.

### Важная асимметрия

- Входящий TCP parser `0x58CCD4` после поиска `\0UniChat\0` читает 4-byte length field и пропускает ещё два байта перед передачей payload в общий parser.

- Не считать outgoing request и incoming response byte-for-byte симметричными. Возможны разные подформаты для FORWARD request и server response, либо разные варианты сообщений, которые используют общий marker.
- Значение global string `0x5959B0`, точная семантика второго аргумента и назначение двух байтов, пропускаемых receive parser, ещё не установлены.

## 46. Сверка предположений ClientConnection с legacy TCP framing — 2026-11-25

### NUL-delimited prefix: внутренняя неоднозначность текущего source

- В текущем `ClientConnection.cs` метод `TryParsePrefix` начинает разбор с byte offset 0 переданного payload и трактует первые три NUL-delimited сегмента как `ClientId`, `marker`, `toUser`.
- В комментарии того же файла приведена legacy-формула:
  - `prefix := #0 + CurID + #0 + 'FORWARD' + #0 + toUser + #0 + 'UniChat' + #0 + tmp`.
- Если первый `#0` в комментарии действительно является первым байтом payload после внешнего decimal header, текущий parser сдвигает поля на один сегмент: первый сегмент будет пустым, затем CurID, затем FORWARD. Это приводит к empty ClientId и закрытию соединения.
- Если же global CurID уже содержит/не содержит ведущий NUL иначе, или комментарий описывает промежуточную строку до дополнительного преобразования, фактический wire layout может отличаться. По одному комментарию это не решается.
- В оригинальном builder `0x579724` глобальная identity string добавляется рядом с literal `\0FORWARD\0`; точное содержимое самой identity string пока не извлечено. Поэтому несовпадение зафиксировано как проверяемая гипотеза, а не как доказанный production defect.

### Внешний decimal length: потенциальный byte-count вопрос

- Текущий `ReadHeaderAsync` читает decimal ASCII до NUL, затем ровно `AdvertisedPayloadLength` байт после этого NUL.
- В комментарии `ClientConnection.cs` legacy sender описан как `IntToStr(Length(AData) + Length(prefix)) + prefix + #0 + AData`.
- Если `Length(prefix)` не включает дополнительный NUL между prefix и AData, указанная формула длины на один байт меньше фактического количества байтов после внешнего header terminator.
- При таком варианте текущий reader оставил бы последний байт AData в TCP stream, что нарушило бы границу следующего кадра. Но необходимо подтвердить, не входит ли этот NUL в один из фактически подсчитываемых string blocks на outgoing path.

### Решение

- Не менять `ClientConnection.cs` и production service на основании этих двух неоднозначностей.
- До правки получить хотя бы один byte-exact legacy TCP frame из контролируемого стенда/безопасной изолированной среды либо закончить статическую реконструкцию всех Delphi string concatenation arguments.
- Затем добавить golden tests:
  1. prefix с ведущим NUL и без него;
  2. exact outer length с дополнительным NUL;
  3. два последовательных frames в одном TCP read;
  4. frame, разбитый на несколько TCP reads;
  5. проверка, что после каждого frame не остаётся хвостовых байтов.

### Следующие действия

1. Проследить инициализацию global identity string и определить, начинается ли её содержимое с NUL.
2. Восстановить точный порядок строковых аргументов `0x405140` в outgoing builder и итоговую длину каждого concatenated block.
3. Сопоставить эти байты с первым NUL-delimited parser в `ClientConnection.cs`.

## 48. Восстановлена последовательность строковых сборок TCP sender 0x579724 — 2026-11-25

### Семантика helper 0x405140

- Функция `0x405140` принимает destination pointer в EAX, количество строк в EDX и строки в stack arguments.
- Она суммирует длины AnsiString по Delphi string headers, выделяет destination buffer и копирует строки в порядке stack-аргументов, начиная с первого pushed (самого глубокого stack argument) до последнего pushed.
- Это позволяет восстанавливать порядок конкатенации по push sequence без предположений по одному лишь расположению литералов.

### Первый plaintext concat перед cipher

- В `0x579724` перед вызовом `0x405140` (count 4) последовательно push-ятся:
  1. literal `UniChat!_ver14`;
  2. исходная строка из первого аргумента sender;
  3. literal `\0FORWARD\0`;
  4. строка из global slot `0x598668` (указатель через `0x5959B0`).
- Destination — local AnsiString `[ebp-0x4]`.
- Таким образом, для этого sender call path plaintext перед cipher формируется как:
  `UniChat!_ver14 + AData + NUL-FORWARD-NUL + LocalIdentity`.
- После этого код проверяет `Network/IsServer` и шифрует подготовленную строку через RC6-CFB8bit. Поэтому `UniChat!_ver14` и этот экземпляр `FORWARD` относятся к внутреннему зашифрованному содержимому, а не к первому cleartext decimal prefix.

### TCP outer envelope

- В TCP branch формируется отдельная 5-byte header string из четырёх байтов packet value и byte flag ('0'/'1').
- Затем второй concat (count 6) строится из:
  - literal `\0FORWARD\0`;
  - global LocalIdentity string;
  - empty-string argument;
  - второго аргумента sender (EDX при входе в `0x579724`);
  - empty-string argument;
  - 5-byte header.
- В результате формируется отдельный metadata string `[ebp-0x0C]`; он не равен зашифрованному plaintext.
- Далее код вычисляет `Length([ebp-0x4]) + Length([ebp-0x0C])`, преобразует сумму в decimal string и выполняет final concat (count 4) в порядке:
  `decimal_length + metadata + NUL-FORWARD-NUL + encrypted_packet`.
- Final string передаётся в TCP socket wrapper `0x55C340`; wrapper получает длину строки и отправляет её через Winsock send. Он сам не добавляет дополнительный decimal prefix или NUL delimiter.

### Выявленное расхождение для дальнейшей проверки

- В final concat присутствует отдельный literal `\0FORWARD\0`, который не очевидно входит в вычисление `Length(encrypted_packet) + Length(metadata)`.
- Если обе копии `FORWARD` действительно присутствуют в metadata и final concat именно в этом порядке, advertised decimal length может не учитывать одну дополнительную 9-байтовую строку. Это статический кандидат на framing discrepancy, а не подтверждённая runtime ошибка.
- Также первый NUL после decimal digits появляется в начале `\0FORWARD\0`; поэтому текущий `TryParsePrefix`, который ожидает ClientId в первом сегменте, не совпадает с этим конкретным реконструированным layout без дополнительной обработки/другого path.
- Нельзя обобщать этот вывод на все сообщения: `0x579724` имеет много call sites, второй аргумент различается, а `Network/IsServer` выбирает TCP/UDP branch.

2. Проверить все AnsiString lengths для литералов `FORWARD`, empty strings, header и LocalIdentity.

## 49. Точная схема TCP stream callback и проверка parser 0x58CCD4 — 2026-11-25

### Callback 0x58CF3C: накопление и выделение полных кадров

- Callback назначается в объекте TCP connection как обработчик по адресу `0x58CF3C` (assignment в `0x58D1C6`).
- Внутри callback поддерживается накопительный буфер; если предыдущий read оставил хвост, он переносится перед добавлением новых байтов.
- Callback ищет первый NUL в decimal ASCII prefix. По длине числового префикса и распознанному числу вычисляет полный размер кадра, затем:
  - при недостатке байтов сохраняет остаток и ждёт следующий read;
  - при наличии полного кадра копирует ровно его в отдельный буфер и вызывает parser `0x58CCD4`;
  - оставшиеся байты сдвигает в начало и повторяет обработку, поэтому несколько кадров в одном read предусмотрены.
- Это подтверждает потоковую обработку fragmented/coalesced TCP reads на уровне callback. Само по себе это не доказывает, что вычисление длины совпадает с sender formula: формулу sender нужно сопоставлять отдельно.
- Рабочий буфер callback ограничивается константами около `0xFF69`/ `0xFF67`; точную прикладную семантику этих лимитов пока не присваивать.

### Parser 0x58CCD4: подтверждённые операции

- Входной аргумент ECX сохраняется как фактическая длина переданного кадра; EDX используется для размера временной копии/буфера.
- Parser сканирует кадр с byte offset 1, ищет ровно 9 байт marker `00 55 6E 69 43 68 61 74 00`, то есть `\0UniChat\0`.
- Пусть `m` — найденный offset marker относительно начала буфера. После marker parser:
  1. читает 4 байта с offset `m + 9` в локальное DWORD;
  2. использует это DWORD как длину создаваемой временной строки;
  3. копирует данные с offset `m + 15` длиной, заданной этим DWORD;
  4. читает пятый байт этой строки (offset 4) как compression flag;
  5. получает GroupKey и вызывает custom key derivation `0x5610C8`, передавая в EDX локальное значение `m` (offset найденного marker);
  6. далее выполняет RC6 decrypt и, при flag ASCII `'1'`, decompression; полученное содержимое передаёт прикладному parser `0x5820C0`.
- Следовательно, в этом parser четыре байта после marker трактуются именно как длина копируемой области, а пятый байт уже внутри этой области — как compression flag. Это отличается от простого предположения «после marker идут packet ID + flag».
- Критически важно: seed, передаваемый в KDF на этом receive path, по фактическому data flow равен позиции marker `m`, а не прочитанному DWORD. Это наблюдение не согласуется напрямую с outgoing builder `0x579724`, где KDF получает случайное 4-byte значение, которое затем копируется в 5-byte header. Причину расхождения пока не установили.

### Корректировка раздела 48: порядок metadata concat

- При повторной проверке call site `0x579724` подтверждён порядок аргументов `405140` по порядку push-инструкций.
- TCP metadata (concat count 6) собирается как:
  `NUL-FORWARD-NUL + LocalIdentity + empty + secondArgument + NUL-UniChat-NUL + fiveByteHeader`.
- В разделе 48 список был неточен: там пропущен literal `\0UniChat\0` и ошибочно указаны два empty-string аргумента. Правильная последовательность содержит один empty-string argument и один marker `\0UniChat\0`.
- Final concat остаётся:
  `decimalLength + metadata + NUL-FORWARD-NUL + encryptedPacket`.
- Эта схема показывает, что в outgoing TCP path marker `\0UniChat\0` непосредственно предшествует пятибайтовому header. Но receive parser трактует первые четыре байта после marker как длину копирования, тогда как sender создаёт их как random value для KDF. Также receive parser использует marker offset как KDF seed. На данный момент это сильное свидетельство, что sender и данный receive parser либо принадлежат разным вариантам/направлениям протокола, либо между ними есть ещё не восстановленное преобразование. Не объявлять это окончательно доказанной несовместимостью без byte-exact frame и анализа всех TCP call paths.

### Решение и следующие действия

1. Не менять framing/parser production code: найдено расхождение в семантике header/KDF, но runtime frame пока отсутствует.
2. Найти все call sites `0x58CCD4` и все присваивания callback `0x58CF3C`, установить, обслуживает ли этот parser именно outgoing path `0x579724` или отдельный socket role.
3. Проверить, какие именно bytes callback передаёт parser: полный кадр с decimal prefix или уже сдвинутую область. По текущему call site передаётся копия полного выделенного кадра, но требуется подтвердить все пути вызова.
4. Сопоставить второй аргумент sender и пятибайтовый header для конкретных TCP call sites; найти возможный преобразователь/обёртку между sender и callback.
5. Получить byte-exact packet на изолированном стенде, затем сделать golden tests для decimal framing, marker offset, DWORD length, KDF seed и compression flag.


## 50. Подтверждён арифметический кандидат на недосчёт TCP frame length — 2026-11-25

### Sender 0x579724: точная арифметика

- В TCP branch зашифрованная строка хранится в локальном AnsiString `[ebp-0x4]`, metadata — в `[ebp-0x0C]`.
- По call sequence `0x57986D–0x57989A` sender получает обе длины через helper `0x405080`, складывает их и преобразует сумму в decimal AnsiString:
  `advertisedLength = Length(encryptedPacket) + Length(metadata)`.
- Final concat `0x405140` (count 4) вызывается после push последовательности:
  1. decimalLength;
  2. metadata;
  3. literal `\0FORWARD\0`;
  4. encryptedPacket.
- Helper `0x405140` обходит varargs в порядке push-инструкций; это подтверждается его stack indexing и последовательностью копирования.
- Следовательно, фактическая строка после decimal prefix имеет структуру:
  `metadata + NUL-FORWARD-NUL + encryptedPacket`.
- В metadata уже есть первая строка `NUL-FORWARD-NUL` (раздел 49), но финальный concat добавляет ещё одну отдельную строку длиной 9 байт. В вычисление advertisedLength входит metadata и encryptedPacket, но не входит эта дополнительная 9-байтовая строка.

### Сверка с TCP callback

- Callback `0x58CF3C` находит NUL после decimal ASCII, преобразует цифры в целое число и вычисляет размер кадра как:
  `decimalDigitCount + 1 + advertisedLength`.
- При таком framing callback выделяет на 9 байт меньше, чем фактически отправляет sender `0x579724`.
- Это уже не просто вопрос трактовки комментария: недостающие 9 байт следуют из конкретной последовательности вычисления суммы и final concat.
- Оговорка по области применимости: sender имеет несколько call sites и TCP/UDP ветви. Вывод относится к исследованной TCP branch `0x579724`; необходимо проверить, что конкретный call site действительно использует эту ветвь и соединяется с callback `0x58CF3C`.

### Последствия, если sender и callback составляют одну пару

- Receiver передаст в `0x58CCD4` только первые `advertisedLength` байт после decimal NUL.
- Оставшиеся 9 байт отдельного `NUL-FORWARD-NUL` останутся в stream buffer и будут восприняты callback как начало следующего decimal prefix.
- Это нарушит границы кадров и может вызвать protocol error/потерю синхронизации на следующем read.
- Такой сценарий объясняет, почему нельзя тестировать только один кадр в отдельном TCP read: обязательны тесты с двумя последовательными кадрами и хвостом после первого.

### Решение

- Не вносить изменение в production parser до установления точного sender call site и реального byte sample.
- При подготовке golden tests добавить два независимых ожидания:
  1. legacy sender formula (advertised length без дополнительного separator);
  2. фактическая длина concatenated bytes после decimal header.
- Отдельно проверить альтернативу: может ли socket wrapper `0x55C340` каким-либо образом исключать/изменять separator. По его текущему disassembly wrapper получает готовую строку и её AnsiString length и отправляет её целиком через Winsock; признаков фильтрации separator нет.

### Следующие действия

1. Классифицировать конкретные TCP call sites `0x579724` и установить, какой из них использует socket object с callback `0x58CF3C`.
2. Найти соответствие между socket object, `IsServer` state и callback registration.
3. Если соответствие подтверждается, подготовить byte-exact synthetic frame и тест, который демонстрирует 9-байтовый остаток после одного кадра.
4. Только после golden test исправлять length calculation в новой ветке; production rollout — отдельным этапом с rollback.


## 51. Сопоставлен sender и callback на одном socket component — 2026-11-25

### Общий объект socket

- TCP callback регистрируется в функции инициализации socket component: объект берётся из `[ebx+0x760]`, а callback pointer `0x58CF3C` записывается в поле объекта `+0x78` (инструкция `0x58D1C6`).
- В TCP send branch `0x579724` тот же компонент получается через global main-form pointer `0x598640` и offset `+0x760`; затем из объекта берётся поле `+0x90` и вызывается wrapper `0x55C340`.
- Инициализирующая функция получает main-form instance в EAX и сохраняет его в EBX; sender использует тот же global main-form instance. Это связывает исследованный sender и callback с одним socket component, а не просто с похожими компонентами в разных модулях.
- Вывод относится к конкретной ветви sender, где установлен TCP socket path. Не распространять на остальные call sites, пока не проверен их runtime state.

### Socket wrapper 0x55C340

- Wrapper получает AnsiString и вызывает `0x405080` для получения её фактической длины.
- Далее передаёт socket handle, указатель на начало строки, эту длину и flags=0 в Winsock send wrapper `0x4B8090`.
- Промежуточной операции, удаляющей или фильтрующей дополнительный `NUL-FORWARD-NUL`, в исследованном пути нет.
- Это подтверждает, что final concat string отправляется целиком, включая отдельный separator длиной 9 байт.

### Уточнённая оценка

- Сопоставление общего socket component + callback registration + send wrapper делает сценарий недосчёта на 9 байт существенно сильнее: sender и stream callback принадлежат одному socket component.
- При этом пока не получен runtime packet capture и не проверены все sender call sites/условия. Поэтому в документации это остаётся статически доказанным расхождением двух операций в одном пути, а production impact — ожидаемым следствием, которое следует подтвердить isolated test.
- Production source и работающий сервер не изменялись.

### Следующий этап

1. Составить минимальный synthetic byte frame по точной последовательности concat, включая decimal header, metadata, дополнительный separator и encrypted placeholder.
2. Прогнать модель callback length calculation: проверить, что первый callback invocation передаёт parser длину на 9 байт меньше и оставляет separator в остаточном буфере.
3. Сформировать unit tests в отдельной рабочей ветке/тестовом проекте, не меняя текущий parser и не затрагивая production.
4. Перед кодовой правкой проверить, что все relevant call sites используют этот TCP branch и что AdvertisedLength нигде не корректируется на более позднем этапе.


## 52. Synthetic framing test уточнил состав 9-байтового остатка — 2026-11-25

### Проверка арифметики на synthetic frame

- Построен изолированный тестовый кадр по восстановленной sender concat sequence:
  `metadata + NUL-FORWARD-NUL + encryptedPacket`.
- Decimal advertised length в тесте вычислен ровно как sender:
  `Length(metadata) + Length(encryptedPacket)`.
- Callback frame length моделируется по восстановленному receive path:
  `decimalDigitCount + 1 + advertisedLength`.
- Для контрольного набора:
  - metadata = 29 bytes;
  - encrypted placeholder = 32 bytes;
  - advertised length = 61;
  - фактическое содержимое после decimal NUL = 70 bytes;
  - callback выделяет 61 byte содержимого;
  - остаётся 9 bytes, равных последним 9 bytes encrypted placeholder.

### Важная коррекция к разделу 50

- Ранее в последствиях было неточно написано, что callback оставляет в stream buffer отдельный separator `NUL-FORWARD-NUL`.
- Это неверно: separator расположен **перед** encryptedPacket и попадает в первые advertisedLength байт. Callback забирает metadata, весь дополнительный separator и только начальную часть encryptedPacket; остатком становятся последние 9 bytes encryptedPacket.
- Значит, parser получает кадр с включённым separator и усечённым ciphertext. Остаток ciphertext затем может быть принят за начало следующего decimal prefix либо склеен с последующими TCP bytes.
- Разница фактической и заявленной длины по-прежнему равна ровно 9 bytes; исправлено только описание того, какие именно байты оказываются в остатке.

### Вывод теста

- Синтетический тест подтверждает арифметическое следствие реконструированной схемы без запуска оригинального EXE и без сетевого воздействия.
- Это не runtime capture и не доказательство того, что любой call site sender использует этот path. Но если конкретный sender call site проходит TCP branch `0x579724` и его socket обслуживается callback `0x58CF3C`, truncation последних 9 ciphertext bytes следует непосредственно из длины и порядка concat.
- Production code не менялся.

### Следующие действия

1. Перенести арифметическую модель в unit test текущего server branch, но пока как regression/specification test без изменения production parser.
2. Добавить варианты ciphertext длиной меньше, равной и больше 9 bytes; проверить точный хвост.
3. Добавить два coalesced frames и fragmented reads, чтобы проверить, как повреждённый остаток влияет на повторную синхронизацию.
4. После этого подготовить отдельный proposed fix с корректной advertised length и совместимостью для обоих вариантов legacy framing.

## 55. Проверена граница совместимости legacy metadata с текущим C# prefix parser — 2026-11-25

### Текущий контракт C# сервера

- `ClientConnection.TryParsePrefix` получает байты сразу после decimal header и читает первые три NUL-delimited поля:
  1. `ClientId`;
  2. `FORWARD`;
  3. `toUser`.
- Для этого контракта первый байт payload должен начинать непустой ClientId. Пример допустимого layout: `alice NUL FORWARD NUL bob NUL ...`.
- Пустой первый сегмент в текущем обработчике приводит к отказу регистрации клиента/закрытию сессии.

### Сопоставление с реконструированным Delphi TCP metadata

- В исследованной TCP branch sender `0x579724` metadata начинается с `NUL-FORWARD-NUL`, затем содержит LocalIdentity, второй аргумент sender, `NUL-UniChat-NUL` и пятибайтовый header.
- Следовательно, если передать этот payload непосредственно в текущий `TryParsePrefix`, первое поле будет пустым, второе — `FORWARD`, третье начнётся с LocalIdentity. Текущий C# parser не сможет принять LocalIdentity как ClientId: он отклонит пустой первый сегмент.
- Это самостоятельное несовпадение форматов, не устраняемое только исправлением advertised length.
- Точное разделение LocalIdentity и второго аргумента пока не установлено; нельзя назначать второй аргумент получателем или трактовать LocalIdentity как ClientId без дополнительных call-site/data-flow доказательств.
- Входящий Delphi parser `0x58CCD4` ориентируется на `NUL-UniChat-NUL`, извлекает следующий DWORD и внутренний buffer. Это также не совпадает с текущей C# моделью первых трёх полей.

### Новый offline compatibility specification

- Добавлен `tests/legacy_tcp_compatibility_spec.py`.
- Тесты проверяют:
  1. текущий C# prefix layout успешно разбирается его контрактом;
  2. реконструированный Delphi metadata layout не проходит этот контракт из-за leading NUL;
  3. corrected length formula, включающая дополнительный separator, потребляет весь synthetic legacy frame;
  4. историческая формула оставляет девятибайтовый хвост.
- На изолированном mirror runner запущены оба Python unittest файла: 8 tests passed (4 framing model + 4 compatibility specification).

### Инженерное решение

- Не реализовывать автоматический fallback, который просто добавляет 9 байт к чтению: это исправило бы только границу кадра, но не формат полей и не семантику parser.

## 56. Обнаружен отдельный однобайтовый framing mismatch в текущем TCP reader — 2026-11-25

### Наблюдение в исходнике

- Комментарий рядом с ClientConnection.TryParsePrefix документирует sender expression:
  `IntToStr(Length(AData) + Length(prefix)) + prefix + #0 + AData`.
- Следовательно, после decimal header фактическое содержимое состоит из `prefix + NUL + AData`, тогда как объявленная длина по этой формуле равна только `Length(prefix) + Length(AData)`.
- В ClientConnection.ReadHeaderAsync длина читается как advertisedPayloadLength; далее HandleClientAsync присваивает wirePayloadLength = advertisedPayloadLength и считывает ровно это количество байт.
- Если приведённая в комментарии sender expression соответствует фактическому wire layout, reader не дочитывает один байт разделителя/тела. Следующий цикл начнёт разбирать оставшийся байт как начало следующего decimal header. Это отдельная арифметическая проблема, не связанная с девятибайтовым недосчётом реконструированного Delphi sender из разделов 48–53.

### Регрессионная модель

- В tests/legacy_tcp_compatibility_spec.py добавлены два offline tests:
  1. моделирование документированного sender expression показывает, что текущая формула чтения оставляет последний байт кадра;
  2. добавление одного байта к advertised length в модели потребляет весь кадр.
- На mirror runner: compatibility specification — 6 tests passed; legacy framing model — 4 tests passed; всего 10 passed.

### Ограничения и решение

- Это вывод из sender expression, оставленного в комментарии C#-исходника, и арифметики текущего reader; он не является packet capture или подтверждением фактического runtime wire bytes.
- Два offline test-файла — спецификационные модели, они не исполняют production C# parser и не подтверждают совместимость с оригинальным EXE.
- ClientConnection.cs, production service и main не менялись. Не вносить механическую поправку +1 в production до проверки фактического Delphi sender call path и согласования с отдельным legacy envelope: прежние разделы уже показывают другие несовпадения metadata и 9-byte separator.
- Следующий этап — восстановить бинарник клиента в рабочем контексте, проследить sender call sites и сравнить реальный сформированный buffer с обеими offline моделями.

## 59. Разделены UDP broadcast port и TCP dedicated port в конфигурации клиента — 2026-11-25

### Подтверждённые INI defaults из кода загрузки конфигурации

Для той же сборки `unichat.exe` (SHA-256 `ca7dfa6520e67e6c5a77287f8160d02b4117b0e69c2a6702dfcbe2986f70766d`) прослежены вызовы чтения ключей из INI:

- `[Network] BroadcastIP`: fallback `255.255.255.255`.
- `[Network] Port`: fallback `17889`.
- `[Network] Auto2Broadcast`: fallback false.
- `[Network] DedicatedIP`: fallback `localhost`.
- `[Network] IsServer`: fallback false.
- `[Network] DedicatedPort`: fallback `6666`.

### Различие двух сетевых путей

- `Network/Port` и `Network/BroadcastIP` передаются в отдельный helper, который создаёт IPv4 datagram socket с аргументами `AF_INET=2`, `SOCK_DGRAM=2`, `IPPROTO_UDP=17`; затем формирует sockaddr с этим адресом и портом и вызывает bind. Это UDP broadcast/discovery path, а не TCP dedicated listener port.
- `DedicatedIP` и `DedicatedPort` передаются в строковый и целочисленный setters socket-объекта; в DFM главной формы присутствует `TClientSocket.Client`. Это dedicated TCP connection path: Host/Port берутся из отдельных настроек, с defaults `localhost:6666`.
- `Network/IsServer` — флаг выбора этого режима: при false startup path инициализирует UDP broadcast socket; при true после установки DedicatedIP/DedicatedPort вызывается `TClientSocket.Active := true`. В DFM setup form `rbBroadcast.Checked = true`, а `rbDedicated` по умолчанию unchecked. Значит, default UI mode — broadcast; true переключает на dedicated TCP. Имя INI-ключа `IsServer` само по себе не доказывает наличие отдельного TCP listener в клиенте.
- Следовательно, значение `17889` нельзя использовать как default TCP port UniChat relay. Оно относится к UDP broadcast socket; default dedicated TCP port остаётся `6666`.
- На production VM при read-only проверке подтверждён listener `192.168.1.2:6666/TCP`; UDP listener на `17889` отсутствует. Это согласуется с архитектурой C# relay: сервер принимает TCP, UDP discovery не реализован. Поэтому клиент в default broadcast mode не обнаружит этот relay через UDP; для подключения к нему следует использовать dedicated TCP settings: `DedicatedIP=192.168.1.2`, `DedicatedPort=6666` (и соответствующий dedicated mode / `IsServer=true`). В момент проверки две клиентские TCP-сессии с `192.168.1.12` и `192.168.1.13` были установлены на `192.168.1.2:6666`.

### Важное расхождение defaults

- В DFM setup form у поля `edIP` сериализован текст `192.168.0.255`.
- При чтении `[Network] BroadcastIP` код передаёт fallback `255.255.255.255` и сохраняет прочитанное значение в отдельную строковую переменную, используемую UDP helper.

## 61. Уточнён wire format актуального Delphi-клиента: dedicated TCP framing совместим с C# reader — 2026-11-25

### Бинарник и подтверждение call path

- Исследована актуальная GitHub-сборка `unichat.exe`: PE32/i386, 2 568 704 байта, SHA-256 `ca7dfa6520e67e6c5a77287f8160d02b4117b0e69c2a6702dfcbe2986f70766d`. EXE не запускался.
- В sender routine VA `0x5A3390` прослежена ветка `Network/IsServer=true` (dedicated TCP). В ней собираются сегменты с текущим ClientId, строковыми константами `NUL-FORWARD-NUL` и `NUL-UniChat-NUL`, адресатом и пятибайтовым inner header.
- Результирующая строка передаётся через `0x568AE0 → 0x568CD0` в socket-send path. В `0x568CD0` виден вызов низкоуровневой отправки с указателем буфера и его длиной.
- Внешний кадр собирается в порядке: десятичная длина, служебный prefix, дополнительный NUL-разделитель, основная часть данных. Длина вычисляется как сумма длин prefix и основной части данных.

### Почему начальный NUL не создаёт пустой ClientId

- Служебный prefix начинается с NUL. В итоговом кадре этот байт стоит сразу после десятичной длины и является именно терминатором внешнего length header.
- После того как C# `ReadHeaderAsync` поглощает этот NUL, начало payload имеет вид `ClientId\0FORWARD\0target\0UniChat\0...`.
- Следующий NUL между prefix и основной частью данных включён в объявленную длину: фактическое число байт после внешнего header равно `(Length(prefix) - 1) + 1 + Length(data)`, то есть `Length(prefix) + Length(data)`. Поэтому для этой сборки нет ни однобайтового недосчёта, ни необходимости прибавлять `+1` к advertised length.
- Первые три NUL-разделённых поля после внешнего header соответствуют контракту C# `TryParsePrefix`: ClientId, marker `FORWARD`, target. Значение `*` остаётся broadcast target.
- Таким образом, текущий dedicated TCP sender актуальной GitHub-сборки согласуется с текущими `ReadHeaderAsync` и `TryParsePrefix` на уровне статически восстановленной структуры кадра.

### Исправление прежних предварительных моделей

- Предыдущие выводы о девятибайтовом недосчёте и однобайтовом framing mismatch из разделов 48–56 нельзя переносить на эту актуальную сборку: они опирались на другую/неполную реконструкцию sender layout и неверно трактовали начальный NUL как часть payload.

## 64. Сверен входящий TCP parser актуального Delphi-клиента с sender и C# relay — 2026-11-25

### Receive callback и границы кадра

- В текущем GitHub EXE найден receive path: callback routine VA `0x5B7050` получает данные через socket receive helper `0x568E58`; helper вызывает Winsock wrapper `0x4BF8CC`.
- Callback поддерживает накопление неполного TCP-потока и обработку нескольких кадров в одном receive buffer. Он находит первый NUL после десятичных цифр, разбирает advertised length и вычисляет полный размер кадра как `decimal_digit_count + 1 + advertised_length`.
- Если в буфере больше одного кадра, callback выделяет первый кадр и сохраняет остаток для следующей итерации; если данных меньше ожидаемого размера, сохраняет фрагмент и ждёт продолжения.
- Затем кадр передаётся inner parser routine VA `0x5B6DE8`. Она ищет девятибайтовый маркер `NUL-UniChat-NUL` (константа в районе VA `0x5B7014`), извлекает четырёхбайтовую часть и пятый байт inner header, после чего выполняет дальнейшую обработку данных.
- Имена event-methods в Delphi RTTI и динамические назначения callback-ов требуют отдельной аккуратной интерпретации; вывод выше основан на фактическом socket receive call path и операциях с буфером, а не только на имени метода.

### Сверка трёх сторон

- Sender `0x5A3390`: `decimal + prefix + NUL + data`; первый байт prefix — NUL terminator внешнего заголовка; advertised length = `Length(prefix) + Length(data)`.
- Client receive callback `0x5B7050`: ожидаемый полный размер = число цифр + один NUL + advertised length. Это в точности равно фактическому размеру sender frame.
- C# server `ReadHeaderAsync`: читает decimal header до NUL и затем ровно advertised bytes; `TryParsePrefix` получает `ClientId\0FORWARD\0target...`. Relay пересылает полный кадр без преобразования.
- Следовательно, статически восстановленные sender, receiver и C# relay framing согласованы для dedicated TCP режима текущей GitHub-сборки. Это сильнее прежней проверки только по sender и серверному parser.
