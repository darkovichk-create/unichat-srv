## 1. Назначение проекта

Изначальная задача — заменить ненадёжную зависимость доставки сообщений от широковещательного обмена между клиентами централизованным TCP-сервером-посредником (relay/router). Клиенты должны подключаться к серверу, а сервер — маршрутизировать сообщения адресатам.

Дальнейшая цель — корпоративная централизованная система сообщений для рабочих станций Windows 10 и Windows 11, с возможностью:
- централизованной регистрации клиентов и отображения присутствия;
- обнаружения/регистрации клиентских устройств;
- удалённой настройки адреса и параметров центрального сервера;
- будущей веб-панели администрирования;
- будущих интеграций с внешними системами, включая Елогика на базе Lotus Notes/Domino, для уведомлений о новых заданиях и документах.

Пользователь предпочитает единый инсталлятор, а не отдельную ручную установку клиента и агента. Целевой сценарий — один установочный пакет для рабочего места, который устанавливает/обновляет совместимый клиент и необходимую службу-агент, если выбранная реализация подтвердит необходимость агента. Это архитектурное требование на будущее, ещё не реализовано.

## 4. Известная архитектура и wire protocol исходного сервера

Текущий сервер — C#/.NET 10 TCP relay:
- первый пакет регистрирует подключившегося клиента под его ID;
- пакеты `FORWARD` направляются конкретному клиенту или всем;
- для каждого клиента используется отдельная очередь и writer task;
- пакеты пересылаются без изменения;
- сервер не хранит историю и не доставляет сообщения отключённым пользователям;
- сервер не реализует UDP discovery;
- исходный максимальный размер тела пакета — 128 KiB.

### Формат пакета (по анализу старого клиентского кода)

Клиент формирует пакет примерно так:

```text
SendText(
  IntToStr(Length(AData) + Length(prefix)) +
  prefix + #0 + AData
);

prefix :=
  #0 + CurID + #0 + 'FORWARD' + #0 +
  toUser + #0 + 'UniChat' + #0 + tmp;
```

Структура на проводе приблизительно:

```text
[ASCII-длина][NUL][NUL][ID отправителя][NUL][FORWARD][NUL]
[получатель][NUL][UniChat][NUL][AData]
```

- Получатель `*` означает широковещательную отправку.
- В legacy-формате объявленная длина не включает дополнительный NUL между prefix и AData. Совместимый сервер должен учитывать это правило (исторически используется `advertisedPayloadLength + 1`).
- Не менять framing/семантику без тестов совместимости с реальным клиентом.
- Серверный relay устраняет необходимость прямой доставки peer-to-peer, только если клиенты действительно подключены к нему и клиентский протокол использует этот путь.
- Централизация доставки сама по себе не гарантирует исправление исчезающих списков/чатов: если проблема связана с обнаружением пользователей, надо отдельно изучить discovery и алгоритмы клиента.
- Обнаружение IP/порта не доказывает, что на устройстве запущен UniChat.
- UDP broadcast обычно не проходит через маршрутизаторы и границы VLAN.

### Файлы и вложения

Сервер не имеет отдельного протокола передачи файлов, хранения файлов или возобновления передачи. Он может ретранслировать бинарные данные в `AData` как есть, если клиент уже кодирует их в совместимом формате и размер укладывается в лимит. Не описывать это как реализованный file-transfer.

## 7. Принятые архитектурные решения (план, ещё не реализация)

Принята гибридная стратегия: сначала обеспечить совместимость с существующим UniChat, параллельно проектировать расширяемую корпоративную платформу и при необходимости новый клиент с привычным интерфейсом. Не переписывать клиент до завершения исследования его протокола и конфигурации.

### Серверные компоненты

Планируемые логические подсистемы:
- **Client Registry** — реестр устройств и клиентских идентификаторов;
- **Presence Service** — онлайн/оффлайн, heartbeat и последнее время активности;
- **Device Management** — состояние и управление зарегистрированными устройствами;
- **Configuration Service** — выдача и версионирование конфигураций;
- **Message Router** — централизованная маршрутизация сообщений;
- **Audit Log** — журнал административных действий и изменений конфигурации;
- **Management API** — отдельный HTTPS API для будущей веб-панели и интеграций;
- **Integration API/Event ingress** — приём внешних событий через аутентифицированный HTTPS API.

Не смешивать административный HTTPS API с legacy TCP wire protocol. Предусмотреть возможность независимого масштабирования и версионирования.

### Обнаружение и регистрация клиентов

Предпочтительный вариант при разрешённой централизованной установке — Windows-служба-агент, поставляемая единым инсталлятором с клиентом/компонентами рабочего места:
- агент регистрирует устройство на сервере;
- отправляет heartbeat и сведения о версии/состоянии;
- получает утверждённую конфигурацию;
- применяет адрес/порт центрального сервера и другие разрешённые параметры;
- сообщает результат применения и поддерживает безопасный откат.

Дополнительные механизмы:
- UDP discovery в локальной сети как вспомогательный механизм;
- DNS SRV или заранее заданный адрес/конфигурация установщика как способ первичного нахождения сервера;
- GPO/AD могут использоваться для централизованного развёртывания единого установщика, если инфраструктура доменная;
- сканирование подсетей не считать достоверным обнаружением запущенного клиента и использовать только как ограниченный вспомогательный механизм.

### Единый инсталлятор

Требование пользователя: единый инсталлятор рабочего места вместо раздельной установки клиента и агента. При проектировании определить:
- состав пакета и поддерживаемые варианты установки/обновления;
- установку/обновление агента как Windows Service;
- права администратора и минимальные привилегии службы;
- корректное удаление, repair и rollback;
- безопасную первоначальную регистрацию устройства;
- подпись установщика и обновлений;
- совместимость с Windows 10 и Windows 11;
- сценарии централизованного развёртывания через GPO/AD;
- возможность установки только совместимого клиента или только компонентов по политике, если это понадобится.

Не проектировать произвольное удалённое выполнение команд на рабочих станциях. Агент должен принимать только ограниченный набор подписанных/аутентифицированных декларативных настроек и безопасных операций.

### Безопасность управления

Обязательные требования:
- аутентификация устройств и сервера;
- авторизация по ролям;
- TLS для HTTPS API и управляющего канала;
- защищённая регистрация устройства и ротация секретов/сертификатов;
- подпись или криптографическая проверка конфигураций;
- аудит выдачи и применения настроек;
- версии конфигураций, подтверждение применения и rollback;
- запрет произвольных shell-команд;
- принцип минимальных привилегий.

### Будущие интеграции

Не связывать ядро сервера напрямую с Lotus Notes. Предусмотреть универсальный Integration API/event ingress и адаптеры. Для Елогика / Lotus Notes-Domino позже потребуется определить доступный интерфейс интеграции (HTTP/API, агент, почтовое событие или иной поддерживаемый механизм), схему идентификаторов сотрудников и подтверждение доставки уведомлений.

Базовая модель: внешняя система передаёт событие (например, новое задание или документ), сервер сопоставляет внешний ID сотрудника с UniChat ID и создаёт уведомление. Нужны идемпотентность, журнал обработки, авторизация источника и статусы доставки. Реализация интеграции отложена.

## 12. Статическая проверка framing и исходников — 2026-11-25

**Ветка:** `fix/tcp-framing-and-deployment`  
**Проверенный blob ClientConnection.cs:** `d9e7bbdf00325fada07e7b01c62e1f8d1d7c5754`

### Уточнение расчёта длины пакета

Ранее возникло предположение, что `advertisedPayloadLength + 1` в исправленной ветке может быть лишним. Повторная сверка с формулой оригинального клиента это предположение опровергла.

Клиент формирует:

```text
IntToStr(Length(AData) + Length(prefix)) + prefix + #0 + AData
prefix := #0 + CurID + #0 + 'FORWARD' + #0 + toUser + #0 + 'UniChat' + #0 + tmp
```

Поскольку `prefix` уже включает начальный NUL, а после него клиент добавляет ещё один NUL перед `AData`, число байтов после NUL-разделителя заголовка равно объявленной длине плюс один. Следовательно, текущая операция `advertisedPayloadLength + 1` в ветке исправлений соответствует legacy-формату. **Не удалять её без теста на пакетах, сформированных оригинальным клиентом.**

### Подтверждённые наблюдения

- `ReadHeaderAsync` в ветке исправлений читает заголовок до NUL и не предполагает, что TCP вернёт 16 байт одним чтением.
- После заголовка код дочитывает точное число байтов тела.
- `TryParsePrefix` разбирает первые четыре поля: пустое начальное поле, ID отправителя, команду и получателя.
- `ConnectionManager` хранит только активные TCP-соединения в ConcurrentDictionary; офлайн-очереди и история отсутствуют.
- Широковещательная отправка проходит по текущим активным соединениям, включая отправителя, если он зарегистрирован в словаре.
- Первый пакет устанавливает ClientId; в исправленной ветке последующие пакеты с отличающимся ID отклоняются.
- `RefCountedBuffer` использует ArrayPool и счётчик ссылок для совместного использования одного буфера между очередями адресатов.
- Настройки клиента из найденных batch/registry файлов расположены под `HKCU\\Software\\UniChat145`; сетевые настройки экспортируются из подраздела `Network`. Имена конкретных параметров сервера пока не установлены.

- Для каждой сессии создана отдельная ограниченная исходящая очередь ёмкостью 256 пакетов.
- При невозможности поставить пакет в очередь соединение закрывается; это ограничивает бесконтрольный рост очередей при медленном/зависшем получателе.
- Максимальный размер тела одного пакета ограничен 128 KiB.
- Пакет маршрутизируется как неизменённый буфер; broadcast проходит по текущим зарегистрированным соединениям.
- TCP Keep-Alive включён; параметры сокета: 30 секунд до первой пробы и 10 секунд между пробами.
- В текущем коде реестр отражает подключённые TCP-сессии; отдельного Presence Service, heartbeat API или постоянного реестра устройств пока нет.
- Обработчики клиентских сессий запускаются фоновыми задачами; listener не хранит отдельный реестр этих задач для ожидания их завершения при остановке. Это следует проверить тестом штатной остановки/перезапуска при открытых соединениях.

### Приоритеты следующего этапа

1. Автоматизировать протокольные тесты: регистрация, личная доставка, broadcast, некорректный/неполный пакет, дубликат ClientId, переполнение очереди.
2. Проверить повторные подключения, параллельные сессии и штатную остановку сервера с активными клиентами.
3. Провести ограниченный нагрузочный/длительный тест с постепенным увеличением числа синтетических клиентов; отдельно фиксировать CPU, RSS, число соединений, рестарты и ошибки.
4. Только после базовой проверки устойчивости менять lifecycle/очереди, если тесты покажут проблему.
5. Presence и управление устройствами реализовывать отдельным новым компонентом/протоколом, не выдавая текущий TCP-реестр за полноценную систему присутствия.

## 21. SQLite-журнал сессий, маршрутизации и ошибок с хранением 20 дней — 2026-11-25

**Ветка:** `fix/tcp-framing-and-deployment`  
**Компоненты:** `AuditLog.cs`, `ClientConnection.cs`, `ConnectionManager.cs`, `TcpServerListener.cs`, `Program.cs`, `UniChatServerd.csproj`.  
**Хранилище на VM:** `/var/lib/unichatd/audit.db`.  
**Режим хранения:** SQLite WAL, UTC timestamps (Unix milliseconds), retention 20 дней.

### Что реализовано

- Добавлен отдельный hosted service `AuditLog`, который асинхронно принимает события из сетевого кода через ограниченную очередь ёмкостью 8192 записи и записывает их пакетами до 128 событий.
- SQLite работает в WAL-режиме; созданы таблица `audit_events` и индексы по времени, ClientId и SessionId.
- Старые события старше 20 дней удаляются при запуске и далее не реже одного раза в час. Выполняется инкрементальная очистка свободных страниц и WAL checkpoint.
- Сбой или временная недоступность БД не должны останавливать TCP relay: AuditLog повторяет подключение с интервалом 5 секунд; при переполнении очереди фиксирует предупреждения о потерянных событиях.
- При штатном завершении очередь журнала закрывается и оставшиеся записи сбрасываются в SQLite.
- В Linux systemd unit добавлен `StateDirectory=unichatd`; каталог БД закрыт правами владельца службы (`0700`), файлы SQLite — `0600`.
- Для self-contained single-file publish включён `IncludeNativeLibrariesForSelfExtract=true`, а `DOTNET_BUNDLE_EXTRACT_BASE_DIR` направлен в `/var/lib/unichatd/.net`.

### Состав аудита и приватность

Сохраняются:
- UTC-время события с точностью до миллисекунд;
- открытие/регистрация/закрытие TCP-сессии, ClientId, IP-адрес и длительность сессии;
- protocol/framing errors, сетевые ошибки, неизвестные команды, дубликаты ClientId, нарушения привязки ID и переполнение очереди;
- маршрутизация личных и broadcast-пакетов, адресат, размер пакета и результат постановки в исходящую очередь;
- запуск/остановка сервера и предупреждения при завершении.

**Тело сообщений и содержимое вложений не сохраняются.** Для сообщений записываются только метаданные. Результат `queued_to_socket_queue(s)` означает постановку в очередь сервера, а не подтверждение фактического получения клиентом.

### Дополнительное исправление жизненного цикла сессий

- `TcpServerListener` теперь отслеживает задачи всех клиентских сессий.

## 30. Уточнение сигнатуры UDP builder 0x579724 — 2026-11-25

### Исправление формулировки раздела 29

- Повторная проверка вызывающих участков показала, что второй аргумент функции `0x579724` в EDX — **указатель на вторую строку**, а не длина.
- Первый аргумент в EAX — указатель на первую строку. Функция сохраняет второй указатель в EBX, затем вызывает helper `0x405270` для получения/обработки длины первой строки; полученное значение участвует в сравнении с 100.
- Поэтому `0x579724` следует описывать как сборщик/отправитель, принимающий две строки (или две Delphi AnsiString), а не как функцию с сигнатурой `(buffer, length)`.
- Внутри функция формирует служебную последовательность, объединяя первую и вторую строки с константными строками/префиксами. В отдельных ветках записывает ASCII `'0'` или `'1'` в локальный буфер; ветвление зависит от длины первой строки.
- После сборки wrapper `0x560F38` отправляет итоговую строку через Winsock `send` на UDP socket handle `0x5984A0`.
- Call sites передают в EDX разные строковые значения: в ряде мест — поля объекта по смещениям `+0x32C` или `+0x324`; в других — указатели на статические Delphi string constants. Это подтверждает, что второй аргумент является строковым фрагментом/значением, а не числовой длиной.

### Значение для дальнейшего анализа

- При восстановлении wire format нужно отслеживать оба строковых аргумента и все конкатенации, а не трактовать EDX как packet length.
- Вызовы `0x579724` встречаются в нескольких разных участках приложения; до анализа контекста каждого call site нельзя сводить их к одному типу события.
- Исправление относится к сигнатуре helper; наблюдения о вызове UDP send через `0x560F38`, socket handle `0x5984A0` и использовании строковых констант остаются подтверждёнными.

## 32. Установлено назначение флага 0x595CB4: Network/IsServer — 2026-11-25

### Источник флага в конфигурации

- Функция загрузки настроек по VA `0x575500` читает INI-секцию `Network`.

### Значение для общего builder/dispatcher 0x579724

- Ранее найденный branch condition по `0x595CB4` теперь имеет установленный конфигурационный источник: это `Network/IsServer`.

Таким образом, серверный режим использует отдельный socket-object send path, а клиентский режим — явно выделенный UDP socket handle.
- Тип сокета альтернативного object path пока не подтверждён непосредственно через его constructor/setup call graph; поэтому не называть его TCP без дополнительной трассировки, хотя в бинарнике отдельно обнаружен TCP stream path.

## 33. Восстановлены параметры UDP broadcast из Network INI — 2026-11-25

### Точное соответствие глобальных переменных INI-настройкам

- Функция загрузки настроек по VA `0x575500` читает строковое значение `Port` из секции `Network`, default string `17889`, и сохраняет его в глобальную строковую переменную по адресу `0x595B64`.

- Следовательно, `Network/Port` и `Network/BroadcastIP` — именно параметры UDP broadcast endpoint; `DedicatedIP` и `DedicatedPort` относятся к отдельной dedicated-серверной конфигурации. Не смешивать эти пары.

### Передача значений в UDP socket setup

- Вызов `0x560E34` по адресу `0x58D25C` получает:
  - EAX: результат преобразования строки `Network/Port` из `0x595B64` в integer через helper `0x409C04`;
  - EDX: строковое значение `Network/BroadcastIP` из `0x595E58`;
  - ECX: HWND, полученный из объекта главной формы.
- Аналогичный вызов `0x560E34` присутствует в другом lifecycle path по адресу `0x584DCD`, который также передаёт integer port, IP string и window handle.
- Внутри `0x560E34` создаются два UDP-сокета `socket(AF_INET, SOCK_DGRAM, IPPROTO_UDP)`.
- Для исходящего сокета `0x5984A0` формируется sockaddr с family AF_INET, портом через `htons(EAX)` и адресом через `inet_addr(EDX)`, после чего выполняется UDP `connect`.

- Это подтверждает, что default UDP peer — broadcast address `255.255.255.255`, а default local UDP port — `17889`, если соответствующие значения не переопределены в `unichat.ini`.

### Значение для архитектуры протокола

- В клиенте явно разделены две конфигурационные пары:
  - UDP broadcast: `Network/BroadcastIP` + `Network/Port` (defaults `255.255.255.255:17889`);

## 35. Восстановлен TCP stream framing и внутренний UniChat marker — 2026-11-25

### TCP ClientRead и reassembly

- Published callback `ClientRead` связан с обработчиком по VA `0x58CF3C`.
- Обработчик вызывает `0x55C6B4`, который выполняет Winsock `recv` через thunk `0x4B8088` (IAT `wsock32.recv`) на socket handle из поля объекта `+4`.
- Вызов принимает буфер размером `0xFF69` байт (65385).
- Если предыдущий фрагмент был неполным, он хранится в глобальном буфере/счётчиках (`0x595B24`, `0x595F54`, флаг `0x595E34`) и объединяется с новыми принятыми байтами.
- Обработчик не предполагает соответствие одного `recv` одному сообщению. Он вычисляет границу полного сообщения, обрабатывает полные сообщения в цикле и сохраняет незавершённый остаток для следующего callback. Это подтверждает TCP stream reassembly и поддержку нескольких сообщений в одном read buffer.

### Внешнее stream framing

- В начале накопленного TCP stream обработчик ищет первый NUL-терминированный ASCII-префикс: он извлекает строку до NUL и преобразует её в integer через helper `0x409C04`.
- Длина префикса и полученное числовое значение используются для вычисления ожидаемой границы кадра: `prefix_length + parsed_integer + 1`.
- Если доступных байтов больше ожидаемой длины, текущий кадр отделяется, передаётся дальше, остаток сдвигается/сохраняется, затем цикл проверяет следующий кадр.
- Если доступных байтов меньше ожидаемой длины, буфер сохраняется как неполный фрагмент.
- Точное соглашение о том, включает ли parsed integer завершающий NUL payload или иные служебные байты, требует проверки по outgoing builder; в этом разделе фиксируется только фактически используемая формула и поведение reassembly.

### Внутренняя структура кадра

- Полный кадр передаётся в parser по VA `0x58CCD4`.
- Parser сканирует данные на девятибайтовый sentinel `00 55 6E 69 43 68 61 74 00`, то есть `NUL + "UniChat" + NUL`.
- Сразу после sentinel копируются четыре байта в integer length field; далее payload извлекается с позиции `sentinel_offset + 15`. Это соответствует 9 байтам sentinel + 4 байтам length + 2 байтам смещения до начала payload по наблюдаемой адресной арифметике; окончательную byte-exact схему следует сверить с builder.
- В извлечённом payload читается byte offset 4. При значении ASCII `'1'` выполняется отдельная ветка; в остальных случаях из payload извлекается остаток, начиная с шестого символа (Delphi 1-based index 6, то есть byte offset 5), и передаётся общему parser `0x5820C0`.
- Таким образом, TCP receive path подтверждает внутренний пятый байт discriminator, уже найденный в UDP receive path, и общий NUL-delimited parser для остатка данных.

### Связь с UDP

- UDP receive path `0x5826D4` отдельно получает датаграмму и также проверяет byte offset 4 на ASCII `'1'`, после чего направляет альтернативную ветку в `0x5820C0`.
- TCP path содержит дополнительный stream framing и sentinel/length parsing до извлечения внутреннего payload.
- Это указывает на общий внутренний формат сообщений поверх двух транспортов, но не доказывает полную идентичность всех полей или byte-for-byte идентичность TCP и UDP пакетов.

### Следующие действия

1. Разобрать точную арифметику длины во внешнем TCP framing и проверить, что именно включает decimal prefix.

## 36. GroupKey участвует в общем 12-байтовом преобразовании сетевых данных — 2026-11-25

### Источник ключа

- При загрузке конфигурации функция `0x575500` читает `GroupKey` из секции `Security` и сохраняет строку в глобальную переменную `0x595A18`.
- Это значение передаётся в helper `0x5610C8` как входная строка.

### Поведение helper 0x5610C8

- Helper нормализует входную строку к 12 байтам:
  - при длине ровно 12 байт копирует все 12;
  - при длине меньше 12 формирует 12-байтовую область с заполнением `0xFF` и копирует исходные байты;
  - при длине больше 12 использует первые 12 байт.
- Затем три 32-битных слова преобразуются серией операций, включающих XOR с константами, rotate, byte-swap, AND и OR. Набор некоторых операций управляется битами второго аргумента (EDX).
- Результат записывается в выходную Delphi string/буфер длиной 12 байт.
- Это собственный key-dependent transform оригинального клиента. По одному дизассемблированию нельзя приписывать ему стандартный криптографический алгоритм или гарантировать криптографическую стойкость.

### Подтверждённые сетевые call sites

- Исходящий builder `0x579724` вызывает `0x5610C8`, передавая строку из `0x595A18`, 32-битное значение, полученное через helper `0x40362C` с аргументом `0x7FFFFFFF`, и локальный output buffer.
- UDP receive processing вызывает тот же helper по адресу `0x58280D`: передаёт `GroupKey`, 32-битное значение из разобранного входящего пакета и локальный output buffer.
- TCP inner-frame parser вызывает тот же helper по адресу `0x58CDF1` с тем же глобальным `GroupKey` и значением из текущего parse context.
- Таким образом, GroupKey-dependent transform встречается в исходящем builder и в обоих входящих transport paths. Это подтверждает, что GroupKey является частью сетевой обработки, а не только локальной настройкой UI.

### Что пока неизвестно

- Не установлено, является ли результат MAC/check value, маскировкой/обфускацией, ключевым преобразованием заголовка или частью другого протокольного механизма.
- Не доказано, что параметр EDX во всех call sites имеет одинаковую семантику; его происхождение отличается по контексту вызова.
- Не восстановлены точные байтовые позиции 12-байтового результата в отправляемой датаграмме/кадре и проверка результата на приёме.
- Не следует называть механизм шифрованием до восстановления полного алгоритма и проверки encode/decode или validation path.

### Следующие действия

1. Проследить использование 12-байтового output из `0x5610C8` в `0x579724`: точное место в outgoing buffer.
2. Проследить UDP receive path после `0x58280D`: с чем сравнивается или как используется output.
3. Разобрать источник EDX в TCP parser и сопоставить его с UDP header field.
4. Построить offline test vectors для одинакового GroupKey и параметров, затем проверить детерминированность/обратимость только на статических данных.
5. Не менять production relay и не реализовывать криптографическую совместимость по неполной гипотезе.


## 37. Подтверждён replay/duplicate packet filter в UDP receive path — 2026-11-25

### Настройки защиты

- Функция загрузки настроек читает из секции `Security`:
  - `EnablePacketFilter`, default false, global byte `0x595FEC`;
  - `NotifyPacketFilter`, default true, global byte `0x595D90`;
  - `PacketBuffer`, default integer 3, global integer `0x5960CC`.
- При загрузке для `PacketBuffer` принудительно устанавливается нижняя граница 3, если конфигурационное значение меньше 3.
- При включённом `EnablePacketFilter` создаётся/настраивается отдельный объект для хранения недавних packet IDs; его ссылка сохраняется в глобальной переменной `0x596014`.

### Поведение UDP receive path

- UDP обработчик `0x5826D4` копирует первые четыре байта входящей датаграммы в integer и отдельно читает byte offset 4 как discriminator.
- При включённом `EnablePacketFilter` вызывается `0x55AEFC` с объектом списка и этим четырёхбайтовым значением.
- Функция `0x55AEFC` проходит по хранимым значениям и сравнивает каждое с входящим ID. При совпадении возвращает true; при отсутствии совпадения добавляет ID в список, а при заполнении ограниченного буфера удаляет старую запись перед добавлением новой.
- Если обнаружен повтор и `NotifyPacketFilter` включён, receive path формирует уведомление с текстом `Обнаружена атака повторными пакетами` через внутренний обработчик события с кодом 9, после чего прекращает обработку текущей датаграммы.
- Независимо от этой опциональной проверки выполняется дополнительная проверка текущего 4-байтового значения с global `0x596050`: равное предыдущему значению отбрасывается; новое значение записывается в global.
- Таким образом, подтверждены как минимум две проверки повторов: простая проверка последнего ID и настраиваемый bounded history filter.

### Связь с GroupKey

- После прохождения packet-filter checks 4-байтовое значение передаётся вместе с `Security/GroupKey` в helper `0x5610C8`.
- Результат helper затем передаётся в cipher-related object path. Точная роль derived 12-byte value в проверке целостности/расшифровании пока исследуется; replay filter и GroupKey transform — отдельные наблюдаемые этапы.

### Ограничения

- Назначение packet ID как nonce/sequence/replay token — наиболее вероятная интерпретация по его использованию, но точное имя поля в wire format пока не установлено.
- Не установлено, очищается ли список при reconnect, смене GroupKey или смене комнаты.
- Этот раздел описывает поведение UDP receive path; не переносить автоматически те же ограничения на TCP без отдельного подтверждения.

### Следующие действия

1. Проследить outgoing builder и подтвердить, что первые четыре байта генерируются как packet ID и передаются без изменения.
2. Проверить, как список packet IDs очищается и как действует при смене GroupKey/переподключении.
3. Разобрать cipher-related object и последующие вызовы после `0x5610C8`, чтобы установить назначение 12-byte transform.
4. Добавить synthetic tests для нового ID, повторного ID, заполненного PacketBuffer и NotifyPacketFilter.


## 38. Идентифицирован криптографический компонент DCPcrypt2 / TDCP_rc6 — 2026-11-25

### RTTI и библиотечные признаки

- В PE присутствуют Delphi RTTI/type names `EDCP_cipher`, `TDCP_cipher`, `TDCP_ciphermode`, `EDCP_blockcipher`, `TDCP_blockcipher`, `TDCP_blockcipher128`, `TDCP_rc6`.
- Обнаружены связанные с DCPcrypt2 строки/unit names `DCPcrypt2`, `DCPblockciphers`, `DCPrc6`, а также алгоритмический литерал `RC6`.
- RTTI для cipher mode перечисляет `cmCBC`, `cmCFB8bit`, `cmCFBblock`, `cmOFB`, `cmCTR`.
- В коде библиотеки присутствуют сообщения `Cipher not initialized` и `Invalid key size`, что подтверждает наличие полноценного cipher component API, а не только одноимённых неиспользуемых строк.

### Связь с сетевым кодом

- В инициализации главной формы по адресу `0x585119` создаётся cipher-related object через class/VMT reference `0x49EA68`; возвращённый объект сохраняется в global `0x598644`.
- В той же области бинарника RTTI содержит класс `TDCP_rc6` и его связь с `TDCP_blockcipher128`; совокупность class metadata, constructor call и cipher exceptions указывает, что global cipher object является реализацией RC6 из DCPcrypt2.
- В outgoing builder `0x579724` и receive paths `0x5826D4`/`0x58CCD4` перед вызовами методов этого объекта выполняется GroupKey-dependent transform `0x5610C8`.
- Полученная 12-байтовая строка передаётся виртуальному методу cipher object вместе с параметром `0x60` (96 decimal). Это соответствует 12-байтовому/96-битному материалу ключа на границе вызова; точную семантику конкретного virtual slot ещё нужно подтвердить по DCPcrypt method table.
- Затем сетевые пути вызывают дополнительные virtual methods cipher object для обработки строк/буферов. Это подтверждает использование cipher component в packet path.

### Что установлено и что нет

- С высокой уверенностью идентифицировано семейство алгоритма: RC6 (DCPcrypt2, TDCP_rc6).
- Наличие режимов CBC/CFB8bit/CFBblock/OFB/CTR подтверждено RTTI.
- Фактически выбранный режим, IV/nonce layout, padding, порядок encrypt/decrypt и точные byte ranges пока не установлены.
- Нельзя считать, что вся UDP/TCP датаграмма целиком шифруется: outer framing и часть header полей явно обрабатываются до cipher-related calls.

### Следующие действия

1. Восстановить virtual method table для `TDCP_rc6` и назначение слотов, вызываемых из `0x579724`, `0x5826D4` и `0x58CCD4`.
2. Найти фактическое значение `CipherMode` после конструктора и до первого packet operation.
3. Проследить, как формируется IV и как cipher method обрабатывает входные/выходные буферы.
4. Сопоставить encrypt path и decrypt path на одинаковом offline test vector.
5. Только после byte-exact проверки добавлять RC6 compatibility в сервер; не менять текущий relay на основании одного RTTI.


## 39. Уточнены параметры RC6 Init: 96-bit derived key и нулевой IV — 2026-11-25

### Идентификация virtual methods

- Глобальный cipher object `0x598644` хранит экземпляр с VMT, связанным с RTTI `TDCP_rc6`.
- В VMT RC6 slot `+0x40` указывает на функцию `0x49DFFC`. Она принимает key string в EDX, key size в ECX и дополнительный IV pointer на стеке.
- Функция `0x49DFFC` передаёт key/key size в базовый cipher initialization path, выполняет RC6 key schedule через virtual method и инициализирует IV.
- При нулевом IV pointer метод заполняет 16 байт внутреннего IV buffer по offset `+0x38` нулями и вызывает дальнейшую инициализацию cipher state.
- В outgoing builder `0x579724` перед вызовом VMT slot `+0x40` на стеке остаётся явный аргумент `0`; helper `0x4052D8` возвращается обычным `ret`, не удаляя этот аргумент. Поэтому для этого вызова IV pointer равен NULL.
- В receive paths повторяется такой же вызов: GroupKey-derived key и key size `0x60` (96 bits), с нулевым IV pointer.

### Ключ и nonce

- Outgoing builder получает 32-битное значение через `0x40362C(0x7FFFFFFF)`, сохраняет его четыре байта и передаёт это значение вместе с `Security/GroupKey` в `0x5610C8`.
- Helper `0x5610C8` выдаёт 12-байтовую строку, которая передаётся в RC6 Init с key size `0x60` = 96 bits.
- UDP receive path извлекает первые четыре байта входящей датаграммы и передаёт их вместе с тем же GroupKey в `0x5610C8`, после чего также инициализирует cipher object 96-битным ключом.
- Это подтверждает per-message key derivation от GroupKey и четырёхбайтового packet value. Точное имя этого поля (nonce/packet ID) в оригинальном протоколе пока не установлено.

### Cipher mode

- Конструктор RC6 object `0x49DE0C` явно устанавливает byte field `[object+0x34] = 0`.
- Базовый cipher code читает этот field как индекс режима и поддерживает пять enum значений из RTTI: `cmCBC`, `cmCFB8bit`, `cmCFBblock`, `cmOFB`, `cmCTR`.
- Первое enum значение `cmCBC` имеет ordinal 0; следовательно, default mode нового RC6 object — CBC.
- В исследованном сетевом lifecycle не обнаружен вызов setter, который переключал бы mode после конструктора. Поэтому CBC является установленным default для созданного сетевого cipher object, пока не найдена другая запись в этот field.

### Ограничения

- 16-байтовый zero IV подтверждён для вызовов Init без IV pointer.
- Точный padding/alignment ciphertext пока не восстановлен. Wrapper выделяет output string по длине input string; block processing и обработка остатка требуют отдельного анализа.
- Не следует автоматически считать, что весь внешний TCP frame или все 5 байт внутреннего header зашифрованы: parser читает header discriminator до decrypt path.
- Хотя outgoing и incoming calls соответствуют encrypt/decrypt направлениям, окончательную byte-level совместимость нужно подтвердить парными тест-векторами.

### Следующие действия

1. Восстановить exact outgoing plaintext, ciphertext и 5-byte inner header offsets.
2. Разобрать RC6 CBC block processing для длины, не кратной 16, и установить padding policy.
3. Подтвердить, что TCP parser использует тот же 96-bit derived key и нулевой IV для каждой отдельной frame.
4. Создать offline RC6-CBC test vectors с GroupKey и nonce; сравнить builder output с receive-side decrypt.
5. Только после совпадения тест-векторов реализовывать совместимость в сервере.
