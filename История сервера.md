## 1. Назначение проекта

Изначальная задача — заменить ненадёжную зависимость доставки сообщений от широковещательного обмена между клиентами централизованным TCP-сервером-посредником (relay/router). Клиенты должны подключаться к серверу, а сервер — маршрутизировать сообщения адресатам.

Дальнейшая цель — корпоративная централизованная система сообщений для рабочих станций Windows 10 и Windows 11, с возможностью:
- централизованной регистрации клиентов и отображения присутствия;
- обнаружения/регистрации клиентских устройств;
- удалённой настройки адреса и параметров центрального сервера;
- будущей веб-панели администрирования;
- будущих интеграций с внешними системами, включая Елогика на базе Lotus Notes/Domino, для уведомлений о новых заданиях и документах.

Пользователь предпочитает единый инсталлятор, а не отдельную ручную установку клиента и агента. Целевой сценарий — один установочный пакет для рабочего места, который устанавливает/обновляет совместимый клиент и необходимую службу-агент, если выбранная реализация подтвердит необходимость агента. Это архитектурное требование на будущее, ещё не реализовано.

## 4. Известная архитектура и wire protocol исходного сервера

Текущий сервер — C#/.NET 10 TCP relay:
- первый пакет регистрирует подключившегося клиента под его ID;
- пакеты `FORWARD` направляются конкретному клиенту или всем;
- для каждого клиента используется отдельная очередь и writer task;
- пакеты пересылаются без изменения;
- сервер не хранит историю и не доставляет сообщения отключённым пользователям;
- сервер не реализует UDP discovery;
- исходный максимальный размер тела пакета — 128 KiB.

### Формат пакета (по анализу старого клиентского кода)

Клиент формирует пакет примерно так:

```text
SendText(
  IntToStr(Length(AData) + Length(prefix)) +
  prefix + #0 + AData
);

prefix :=
  #0 + CurID + #0 + 'FORWARD' + #0 +
  toUser + #0 + 'UniChat' + #0 + tmp;
```

Структура на проводе приблизительно:

```text
[ASCII-длина][NUL][NUL][ID отправителя][NUL][FORWARD][NUL]
[получатель][NUL][UniChat][NUL][AData]
```

- Получатель `*` означает широковещательную отправку.
- В legacy-формате объявленная длина не включает дополнительный NUL между prefix и AData. Совместимый сервер должен учитывать это правило (исторически используется `advertisedPayloadLength + 1`).
- Не менять framing/семантику без тестов совместимости с реальным клиентом.
- Серверный relay устраняет необходимость прямой доставки peer-to-peer, только если клиенты действительно подключены к нему и клиентский протокол использует этот путь.
- Централизация доставки сама по себе не гарантирует исправление исчезающих списков/чатов: если проблема связана с обнаружением пользователей, надо отдельно изучить discovery и алгоритмы клиента.
- Обнаружение IP/порта не доказывает, что на устройстве запущен UniChat.
- UDP broadcast обычно не проходит через маршрутизаторы и границы VLAN.

### Файлы и вложения

Сервер не имеет отдельного протокола передачи файлов, хранения файлов или возобновления передачи. Он может ретранслировать бинарные данные в `AData` как есть, если клиент уже кодирует их в совместимом формате и размер укладывается в лимит. Не описывать это как реализованный file-transfer.

## 7. Принятые архитектурные решения (план, ещё не реализация)

Принята гибридная стратегия: сначала обеспечить совместимость с существующим UniChat, параллельно проектировать расширяемую корпоративную платформу и при необходимости новый клиент с привычным интерфейсом. Не переписывать клиент до завершения исследования его протокола и конфигурации.

### Серверные компоненты

Планируемые логические подсистемы:
- **Client Registry** — реестр устройств и клиентских идентификаторов;
- **Presence Service** — онлайн/оффлайн, heartbeat и последнее время активности;
- **Device Management** — состояние и управление зарегистрированными устройствами;
- **Configuration Service** — выдача и версионирование конфигураций;
- **Message Router** — централизованная маршрутизация сообщений;
- **Audit Log** — журнал административных действий и изменений конфигурации;
- **Management API** — отдельный HTTPS API для будущей веб-панели и интеграций;
- **Integration API/Event ingress** — приём внешних событий через аутентифицированный HTTPS API.

Не смешивать административный HTTPS API с legacy TCP wire protocol. Предусмотреть возможность независимого масштабирования и версионирования.

### Обнаружение и регистрация клиентов

Предпочтительный вариант при разрешённой централизованной установке — Windows-служба-агент, поставляемая единым инсталлятором с клиентом/компонентами рабочего места:
- агент регистрирует устройство на сервере;
- отправляет heartbeat и сведения о версии/состоянии;
- получает утверждённую конфигурацию;
- применяет адрес/порт центрального сервера и другие разрешённые параметры;
- сообщает результат применения и поддерживает безопасный откат.

Дополнительные механизмы:
- UDP discovery в локальной сети как вспомогательный механизм;
- DNS SRV или заранее заданный адрес/конфигурация установщика как способ первичного нахождения сервера;
- GPO/AD могут использоваться для централизованного развёртывания единого установщика, если инфраструктура доменная;
- сканирование подсетей не считать достоверным обнаружением запущенного клиента и использовать только как ограниченный вспомогательный механизм.

### Единый инсталлятор

Требование пользователя: единый инсталлятор рабочего места вместо раздельной установки клиента и агента. При проектировании определить:
- состав пакета и поддерживаемые варианты установки/обновления;
- установку/обновление агента как Windows Service;
- права администратора и минимальные привилегии службы;
- корректное удаление, repair и rollback;
- безопасную первоначальную регистрацию устройства;
- подпись установщика и обновлений;
- совместимость с Windows 10 и Windows 11;
- сценарии централизованного развёртывания через GPO/AD;
- возможность установки только совместимого клиента или только компонентов по политике, если это понадобится.

Не проектировать произвольное удалённое выполнение команд на рабочих станциях. Агент должен принимать только ограниченный набор подписанных/аутентифицированных декларативных настроек и безопасных операций.

### Безопасность управления

Обязательные требования:
- аутентификация устройств и сервера;
- авторизация по ролям;
- TLS для HTTPS API и управляющего канала;
- защищённая регистрация устройства и ротация секретов/сертификатов;
- подпись или криптографическая проверка конфигураций;
- аудит выдачи и применения настроек;
- версии конфигураций, подтверждение применения и rollback;
- запрет произвольных shell-команд;
- принцип минимальных привилегий.

### Будущие интеграции

Не связывать ядро сервера напрямую с Lotus Notes. Предусмотреть универсальный Integration API/event ingress и адаптеры. Для Елогика / Lotus Notes-Domino позже потребуется определить доступный интерфейс интеграции (HTTP/API, агент, почтовое событие или иной поддерживаемый механизм), схему идентификаторов сотрудников и подтверждение доставки уведомлений.

Базовая модель: внешняя система передаёт событие (например, новое задание или документ), сервер сопоставляет внешний ID сотрудника с UniChat ID и создаёт уведомление. Нужны идемпотентность, журнал обработки, авторизация источника и статусы доставки. Реализация интеграции отложена.

## 12. Статическая проверка framing и исходников — 2026-11-25

**Ветка:** `fix/tcp-framing-and-deployment`  
**Проверенный blob ClientConnection.cs:** `d9e7bbdf00325fada07e7b01c62e1f8d1d7c5754`  
**Статус:** статический анализ; сборка и runtime-тесты не выполнены.

### Уточнение расчёта длины пакета

Ранее возникло предположение, что `advertisedPayloadLength + 1` в исправленной ветке может быть лишним. Повторная сверка с формулой оригинального клиента это предположение опровергла.

Клиент формирует:

```text
IntToStr(Length(AData) + Length(prefix)) + prefix + #0 + AData
prefix := #0 + CurID + #0 + 'FORWARD' + #0 + toUser + #0 + 'UniChat' + #0 + tmp
```

Поскольку `prefix` уже включает начальный NUL, а после него клиент добавляет ещё один NUL перед `AData`, число байтов после NUL-разделителя заголовка равно объявленной длине плюс один. Следовательно, текущая операция `advertisedPayloadLength + 1` в ветке исправлений соответствует legacy-формату. **Не удалять её без теста на пакетах, сформированных оригинальным клиентом.**

### Подтверждённые наблюдения

- `ReadHeaderAsync` в ветке исправлений читает заголовок до NUL и не предполагает, что TCP вернёт 16 байт одним чтением.
- После заголовка код дочитывает точное число байтов тела.
- `TryParsePrefix` разбирает первые четыре поля: пустое начальное поле, ID отправителя, команду и получателя.
- `ConnectionManager` хранит только активные TCP-соединения в ConcurrentDictionary; офлайн-очереди и история отсутствуют.
- Широковещательная отправка проходит по текущим активным соединениям, включая отправителя, если он зарегистрирован в словаре.
- Первый пакет устанавливает ClientId; в исправленной ветке последующие пакеты с отличающимся ID отклоняются.
- `RefCountedBuffer` использует ArrayPool и счётчик ссылок для совместного использования одного буфера между очередями адресатов.
- Настройки клиента из найденных batch/registry файлов расположены под `HKCU\\Software\\UniChat145`; сетевые настройки экспортируются из подраздела `Network`. Имена конкретных параметров сервера пока не установлены.

- Для каждой сессии создана отдельная ограниченная исходящая очередь ёмкостью 256 пакетов.
- При невозможности поставить пакет в очередь соединение закрывается; это ограничивает бесконтрольный рост очередей при медленном/зависшем получателе.
- Максимальный размер тела одного пакета ограничен 128 KiB.
- Пакет маршрутизируется как неизменённый буфер; broadcast проходит по текущим зарегистрированным соединениям.
- TCP Keep-Alive включён; параметры сокета: 30 секунд до первой пробы и 10 секунд между пробами.
- В текущем коде реестр отражает подключённые TCP-сессии; отдельного Presence Service, heartbeat API или постоянного реестра устройств пока нет.
- Обработчики клиентских сессий запускаются фоновыми задачами; listener не хранит отдельный реестр этих задач для ожидания их завершения при остановке. Это следует проверить тестом штатной остановки/перезапуска при открытых соединениях.

### Приоритеты следующего этапа

1. Автоматизировать протокольные тесты: регистрация, личная доставка, broadcast, некорректный/неполный пакет, дубликат ClientId, переполнение очереди.
2. Проверить повторные подключения, параллельные сессии и штатную остановку сервера с активными клиентами.
3. Провести ограниченный нагрузочный/длительный тест с постепенным увеличением числа синтетических клиентов; отдельно фиксировать CPU, RSS, число соединений, рестарты и ошибки.
4. Только после базовой проверки устойчивости менять lifecycle/очереди, если тесты покажут проблему.
5. Presence и управление устройствами реализовывать отдельным новым компонентом/протоколом, не выдавая текущий TCP-реестр за полноценную систему присутствия.

Этот аудит не является результатом нагрузочного теста и не меняет статус работающей службы.


## 20. Контролируемый тест параллельных подключений и broadcast — 2026-11-25

**Ветка исходников:** `fix/tcp-framing-and-deployment`  
**Тестовый сервер:** `srv-unichat`, `192.168.1.2:6666`.  
**Источник тестовых подключений:** `srv-git`, локальная сеть.  
**Изменения бинарника/конфигурации:** не выполнялись.

### Методика

- Запущен временный синтетический тестовый клиент на Python, подключивший 16 одновременных TCP-сессий.
- Каждая сессия зарегистрировалась отдельным ClientId штатным legacy framing и отправила тестовый пакет на несуществующий адресат, чтобы не создавать лишний трафик реальным пользователям.
- После регистрации все 16 сессий получили 20 последовательных broadcast-пакетов.
- Для каждой из 320 ожидаемых доставок проверялось полное побайтное совпадение полученного wire-пакета с отправленным.
- По завершении теста все синтетические соединения закрыты. Рабочие Windows-клиенты не изменялись и не отключались.

### Результат

- **PASS:** 16 параллельных синтетических клиентов.
- **PASS:** 20 broadcast-раундов.
- **PASS:** 320 из 320 доставок, содержимое каждого пакета совпало побайтно.
- Время цикла broadcast-проверки — около 0.005 секунды; наблюдаемая скорость в этой локальной тестовой конфигурации — около 65.9 тыс. доставок/с.
- Это короткий тест небольших пакетов в локальной сети, а не измерение предельной пропускной способности: он не моделирует WAN, реальные пользовательские сообщения, большие вложения, длительную нагрузку и медленных получателей.

### Состояние сервера после теста

- `unichatd.service` — `active`, `NRestarts=0`.
- `MemoryCurrent` — около 17 MiB после теста (до него около 16 MiB).
- Load average — `0.00, 0.00, 0.00`.
- Два исходных TCP-подключения Windows-клиентов на порту 6666 остались в состоянии `ESTABLISHED`.
- Синтетические TCP-сессии закрылись; дополнительных постоянных соединений после теста не осталось.

### Выводы и следующий этап

- Базовая параллельная регистрация и broadcast проверены на 16 одновременных сессиях без потери/изменения тестовых пакетов.
- Нагрузка такого теста практически не повлияла на ресурсы VM.
- Штатная остановка сервера при открытых сессиях пока не проверялась. Повторный статический аудит выявил, что `TcpServerListener` запускает обработчики сессий как фоновые задачи, но не хранит их для явного ожидания завершения при остановке. Это потенциальный lifecycle-риск, а не подтверждённая неисправность. Следующий безопасный шаг — добавить отслеживание задач и ожидание завершения в `StopAsync`, покрыть сценарий сборкой и отдельным тестом до выкладки.
- Далее: проверить серию reconnect и поведение при медленном/нечитающем получателе; затем провести более длительный soak-test. Presence, файловый протокол и централизованное управление устройствами остаются отдельными будущими компонентами и не считаются реализованными.


## 21. SQLite-журнал сессий, маршрутизации и ошибок с хранением 20 дней — 2026-11-25

**Ветка:** `fix/tcp-framing-and-deployment`  
**Компоненты:** `AuditLog.cs`, `ClientConnection.cs`, `ConnectionManager.cs`, `TcpServerListener.cs`, `Program.cs`, `UniChatServerd.csproj`.  
**Хранилище на VM:** `/var/lib/unichatd/audit.db`.  
**Режим хранения:** SQLite WAL, UTC timestamps (Unix milliseconds), retention 20 дней.

### Что реализовано

- Добавлен отдельный hosted service `AuditLog`, который асинхронно принимает события из сетевого кода через ограниченную очередь ёмкостью 8192 записи и записывает их пакетами до 128 событий.
- SQLite работает в WAL-режиме; созданы таблица `audit_events` и индексы по времени, ClientId и SessionId.
- Старые события старше 20 дней удаляются при запуске и далее не реже одного раза в час. Выполняется инкрементальная очистка свободных страниц и WAL checkpoint.
- Сбой или временная недоступность БД не должны останавливать TCP relay: AuditLog повторяет подключение с интервалом 5 секунд; при переполнении очереди фиксирует предупреждения о потерянных событиях.
- При штатном завершении очередь журнала закрывается и оставшиеся записи сбрасываются в SQLite.
- В Linux systemd unit добавлен `StateDirectory=unichatd`; каталог БД закрыт правами владельца службы (`0700`), файлы SQLite — `0600`.
- Для self-contained single-file publish включён `IncludeNativeLibrariesForSelfExtract=true`, а `DOTNET_BUNDLE_EXTRACT_BASE_DIR` направлен в `/var/lib/unichatd/.net`.

### Состав аудита и приватность

Сохраняются:
- UTC-время события с точностью до миллисекунд;
- открытие/регистрация/закрытие TCP-сессии, ClientId, IP-адрес и длительность сессии;
- protocol/framing errors, сетевые ошибки, неизвестные команды, дубликаты ClientId, нарушения привязки ID и переполнение очереди;
- маршрутизация личных и broadcast-пакетов, адресат, размер пакета и результат постановки в исходящую очередь;
- запуск/остановка сервера и предупреждения при завершении.

**Тело сообщений и содержимое вложений не сохраняются.** Для сообщений записываются только метаданные. Результат `queued_to_socket_queue(s)` означает постановку в очередь сервера, а не подтверждение фактического получения клиентом.

### Дополнительное исправление жизненного цикла сессий

- `TcpServerListener` теперь отслеживает задачи всех клиентских сессий.
- При `StopAsync` сначала прекращается приём новых подключений, затем сервер ожидает завершения оставшихся сессий до 15 секунд и фиксирует `shutdown_warning`, если drain не завершился в срок.
- `ConnectionManager.RemoveConnection` теперь удаляет пару ClientId/connection атомарно, чтобы позднее закрытие старой сессии не удалило новую сессию с тем же ClientId после быстрого reconnect.

### Проверки

- На тестовой копии проекта: `dotnet build UniChatServerd.csproj -c Release` — **Build succeeded, 0 Warning(s), 0 Error(s)**.
- Self-contained single-file публикация для `linux-x64` проверена; с включённым native self-extract SQLite открыла тестовую БД и корректно запустила/остановила процесс.
- Интеграционный тест двумя синтетическими клиентами подтвердил личную доставку и broadcast; SQLite содержала события `session_open`, `client_connected`, `message_routed`, `session_closed`. Тело тестовых сообщений в таблицу не попадало.
- На первом пробном развёртывании выяснилось, что native `e_sqlite3` не был включён в single-file bundle. Предыдущий рабочий бинарник был немедленно восстановлен из резервной копии; сервис вернулся в `active`. Затем публикация исправлена параметром `IncludeNativeLibrariesForSelfExtract` и задан каталог извлечения. Не считать первый неудачный бинарник действующим.
- После исправленного развёртывания: `unichatd.service` — `active`, `NRestarts=0`; в journald подтверждено открытие `/var/lib/unichatd/audit.db`.
- На рабочем сервере SQLite содержит реальные события регистрации двух штатных клиентов и маршрутизации broadcast-пакетов. ### Ограничения и следующие шаги

- Текущее поле `message_routed` фиксирует факт постановки пакета в очередь отправки, но legacy-протокол не предоставляет серверу подтверждение отображения/прочтения у адресата. Не трактовать это как end-to-end delivery receipt.
- Данные доступны локально администратору с правами чтения файла; веб-интерфейс просмотра пока не реализован.
- Проверить retention на искусственно состаренных записях и длительную работу WAL/очистки.
- Добавить read-only отчёт/Management API для будущей веб-панели, не открывая SQLite напрямую в сеть.
- Не включать содержимое сообщений в аудит без отдельного решения по политике хранения и приватности.
